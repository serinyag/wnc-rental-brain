# 7.2D Phase 5 Current-Governed-Knowledge Wrapper

## Wrapper entry point

Phase 7.2D adds `tools/phase_07_reasoning/phase5_wrapper.py` with one stable application-layer entry point:

- `execute_phase5_plan(...)`

The function accepts a validated `QueryPlan`, optional `QueryContext`, optional `Phase7RuntimeConfiguration`, and injectable dependencies for query execution, model lookup, query embedding, retrieval, metadata enrichment, and relationship enrichment. It returns one `LayerExecutionRecord` for `phase_5`.

## Input contract

The wrapper consumes the Phase 5 slice of the validated plan:

- `query_plan.phase_5.required`
- `query_plan.phase_5.query_text`
- `query_plan.phase_5.filters.document_code`
- `query_plan.phase_5.filters.category_code`
- `query_plan.phase_5.filters.rental_type_code`

If Phase 5 is not requested, the wrapper returns:

- `layer_id = phase_5`
- `requested = false`
- `execution_state = not_requested`
- `result_count = 0`

No model lookup, OpenAI call, or Phase 5 retrieval executes on this path.

## Healthy hybrid path

Healthy execution follows the frozen Phase 5 production path:

1. select the Phase 5 query text from `query_plan.phase_5.query_text`, else the plan query text
2. normalize the query text using the existing Phase 5 helper
3. resolve the single active retrieval-approved embedding model
4. construct `EmbeddingModelConfig` from repository model metadata
5. verify current-corpus embedding coverage
6. generate the query embedding using `OpenAIEmbeddingsClient` and `embed_query_text(...)`
7. call `tools.phase_05_search.search_hybrid.run_hybrid_search(...)`
8. preserve database row ordering
9. normalize returned rows into frozen Phase 7 envelopes

The wrapper does not add post-retrieval reranking.

## Embedding model/config resolution

The wrapper performs preflight checks before calling hybrid retrieval:

- active retrieval-approved model must exist and be unique
- model configuration JSON must be present and usable
- current embedding coverage must resolve successfully
- eligible current chunks must be non-zero
- embedded current chunks must match eligible current chunks

Coverage is resolved from:

- `private.current_knowledge_chunk_embedding_inputs`
- `private.knowledge_embeddings`

## Fallback policy

If the semantic path cannot be honestly labeled healthy, the wrapper does not report `hybrid`. It switches to explicit lexical fallback:

- retrieval mode used: `fts_fallback`
- layer execution state: `fallback`
- fallback metadata populated on the layer and each normalized result

Fallback uses `private.search_knowledge_chunks(...)` through a bounded wrapper query and preserves the same Phase 7 result contract shape.

## Retrieval-mode labeling

Stable top-level retrieval labeling is:

- healthy: `hybrid`
- degraded but usable: `fts_fallback`
- retrieval unavailable: `unavailable`
- technical execution error: `failed`
- valid empty retrieval: `no_results`

## Source-role normalization

Every normalized Phase 5 result is explicitly stamped as current governed knowledge:

- `source_layer_role = current_governed_knowledge`
- `authority_tier_code = current_governed`
- `authority_priority = 2`

The native Phase 5 `authority_classification` field remains preserved in the layer payload and does not drive shared-contract authority normalization.

## Result normalization

Each retrieved chunk is normalized into `NormalizedResultEnvelope` with:

- stable identity keyed by `document_code`
- exact identity carrying `document_version_id`, `document_version_number`, `chunk_id`, and `chunk_set_id`
- `summary_text` equal to the governed chunk body text
- shared `RetrievalMetadata`
- shared `ProvenanceEnvelope`
- shared `SensitivityEnvelope`
- native Phase 5 row fields preserved in `layer_payload`

Normalized Phase 5 items use:

- `execution_state = success` on healthy hybrid
- `execution_state = fallback` on lexical fallback
- `reasoning_state = null`

## Confidentiality augmentation

The wrapper enriches each returned chunk with bounded confidentiality metadata from the current governed corpus:

- `private.current_knowledge_chunks`
- `public.knowledge_document_versions`
- `public.knowledge_confidentiality_levels`

Supported live values now include:

- `externally_shareable`
- `internal`
- `commercially_sensitive`
- `restricted`

If metadata resolution fails, the wrapper defaults conservatively to `restricted` and marks the sensitivity payload with `conservative_restricted_default_applied`.

## PI augmentation

The wrapper enriches each chunk with Phase 5 source-object PI status using:

- `public.knowledge_source_objects.personal_information_status`
- `private.strictest_personal_information_status(...)`

The normalized envelope preserves the existing tri-state:

- `yes`
- `no`
- `unknown`

When PI cannot be resolved, the wrapper falls back to `unknown`.

## Provenance handling

The wrapper preserves direct retrieval provenance and bounded source identity metadata:

- `primary_chunk_source_id`
- `primary_document_version_source_object_id`
- `primary_source_locator`
- source object identity
- source registry identity
- source codes
- additional locators
- bounded source trace records

The provenance envelope remains metadata-only. The wrapper does not fetch or expose raw source documents.

## Phase 4 relationship enrichment

The wrapper performs bounded enrichment only for returned Phase 5 rows. It reads, but does not execute, Phase 4-adjacent governance relationship tables:

- `public.knowledge_document_version_logical_rules`
- `public.knowledge_document_version_rule_versions`
- `private.knowledge_chunk_logical_rules`
- `private.knowledge_chunk_rule_versions`
- `public.knowledge_rule_relationship_types`

Relationship metadata is attached to the Phase 5 `layer_payload` as `phase_4_rule_relationships`. Relationship scope is preserved as either `chunk` or `document_version`. This enrichment does not change the result source role.

## Error semantics

The wrapper distinguishes:

- query validation failure
- embedding model resolution failure
- embedding configuration failure
- embedding coverage failure
- query embedding failure
- hybrid retrieval failure
- FTS fallback failure
- partial enrichment failure

Sensitivity/provenance enrichment failures degrade conservatively without inventing new execution states. The wrapper surfaces safe warning metadata through `error_category` and `safe_error_message` on otherwise successful results.

## No-results semantics

If retrieval executes successfully but returns no rows, the wrapper returns:

- `execution_state = no_results`
- `result_count = 0`
- no normalized items

This is a retrieval outcome, not an authority-resolution outcome.

## Security posture

The wrapper:

- reuses existing environment loading and OpenAI client code
- does not leak DB internals into serialized safe errors
- does not expose raw source content beyond governed Phase 5 chunk text
- defaults conservatively on unresolved sensitivity
- preserves PI metadata without returning raw personal data

## Explicit deferred scope

7.2D intentionally does not implement:

- Phase 6 adapter execution
- cross-layer context assembly
- cross-layer authority resolution
- contamination handling
- cross-layer confidentiality resolution
- answer generation
- RAG orchestration
- agent workflows
- Phase 7 persistence
