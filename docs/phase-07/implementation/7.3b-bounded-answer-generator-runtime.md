## Runtime Entry Point

Implemented stable entry point:

- `tools.phase_07_reasoning.answer_generator.generate_bounded_answer(...)`

This orchestrator performs:

1. input acceptance
2. pre-generation decision enforcement
3. bounded request assembly
4. injected generator invocation when permitted
5. structured response parsing
6. deterministic answer validation
7. fail-closed runtime result construction

## Provider-Neutral Generator Interface

Implemented:

- `BoundedAnswerGenerator` protocol

Interface shape:

- `generate(request: BoundedAnswerGeneratorRequest) -> object`

Deliberate exclusions:

- no OpenAI SDK
- no Anthropic SDK
- no HTTP client
- no API keys
- no provider response types

## Generator Request Boundary

Implemented request contract:

- `BoundedAnswerGeneratorRequest`

The generator receives only `AnswerGenerationInput`-derived safe data:

- query text
- semantic answer mode
- authority outcome
- generation decision
- confirmation and insufficient-authority flags
- degraded-state flags
- immutable rules
- authority hierarchy
- prohibited behaviors
- answer-mode instruction
- restriction instructions
- degraded-state instruction when applicable
- claim frames
- safe grounding
- required warning codes
- structured output schema fields
- forbidden response fields

The request does not contain:

- raw `ContextPackage`
- raw layer contexts
- layer execution objects
- suppressed source items
- raw provenance payloads
- adapters
- retrieval callables
- database handles

## Pre-Generation Enforcement

Implemented behavior:

- `blocked` -> zero generator calls, deterministic blocked `AnswerResult`
- `allowed` -> one bounded generator call permitted
- `allowed_with_restrictions` -> one bounded generator call permitted with explicit restriction instructions and already-limited safe claim frames

Enforcement occurs application-side before any generator invocation.

## Prompt / Request Assembly

7.3B keeps provider-neutral prompt assembly separate from provider execution.

Assembly includes:

- immutable bounded-generation rules
- authority hierarchy
- prohibited behaviors
- deterministic answer-mode instruction
- restricted-answer instructions where applicable
- degraded-state instruction when material
- generator-safe claim frames
- generator-safe grounding
- required output schema

No chain-of-thought or hidden reasoning fields are requested.

## Parsing Behavior

Implemented deterministic parser:

- `_parse_generator_response(...)`

Accepted structured inputs:

- `AnswerResult`
- plain dict matching the bounded response schema

Rejected:

- non-dict unstructured output
- forbidden fields like `chain_of_thought`
- unexpected keys
- malformed grounding structures
- invalid `AnswerResult` payloads

Malformed outputs fail closed with:

- `malformed_generator_response`

## Post-Generation Validation

7.3B reuses:

- `validate_answer_result(...)`

Validation remains the single deterministic post-generation authority/safety gate.

Used runtime checks include:

- authority outcome preservation
- answer-mode preservation
- generation-decision preservation
- confirmation preservation
- insufficient-authority preservation
- degraded-state preservation
- safe grounding membership
- claim/grounding role alignment
- blocked-state enforcement
- warning preservation

## Failure Taxonomy

Implemented runtime failure codes:

- `invalid_generation_input`
- `generation_blocked`
- `generator_failure`
- `generator_timeout`
- `malformed_generator_response`
- `answer_validation_failed`

The taxonomy stays intentionally small and machine-inspectable.

## Runtime Result Boundary

Implemented:

- `BoundedAnswerRuntimeResult`

It records:

- runtime status
- whether the generator was called
- failure code
- failure details
- delivered `AnswerResult` when safe
- delivered validation result when safe
- bounded generator request
- raw structured generator response payload when available

Only validated `AnswerResult` objects cross the delivery boundary.

## Implementation Choices

### Request-scoped safe grounding identity

7.3B tightened 7.2G generator-safe grounding IDs from ordinal-only form to item-based form:

- from `generator_safe:1`
- to `generator_safe:{item_id}`

Reason:

- ordinal-only IDs could collide across requests
- item-based IDs remain safe while making cross-request grounding reuse rejectable

### Safe failure results

When generator invocation, parsing, or validation fails, the runtime returns a safe failed `AnswerResult` aligned to upstream metadata instead of exposing invalid generated output.
