# Phase 7.2C Phase 4 Adapter Execution & Normalization

Date: August 8, 2026

## Adapter entry point

Phase 7.2C adds the Phase 4 application-layer adapter at:

- `tools/phase_07_reasoning/phase4_adapter.py`

The stable entry point is:

- `execute_phase4_plan(query_plan, query_context=None, runtime_configuration=None, query_runner=None)`

The adapter accepts a validated `QueryPlan`, optional `QueryContext`, optional adapter configuration, and an injectable SQL execution dependency.

It returns one frozen Phase 7 `LayerExecutionRecord` for `phase_4`.

## Domain registry

The adapter uses a registry instead of a large conditional executor.

Registered Phase 4 domains:

- `booking_fee`
- `payment`
- `expedited_surcharge`
- `cancellation`
- `capacity`
- `space_access`
- `operational_requirements`
- `catering_supplier`
- `technical_inventory`
- `technical_capability`
- `service_rules`
- `facilitator_requirements`

Each registry entry declares the domain code, the Phase 4 RPC surface(s), and a focused handler.

## Parameter resolution

The adapter resolves parameters only from:

- `query_plan.phase_4.domain_inputs`
- safe defaults already supported by the Phase 4 RPCs

`QueryContext` remains available for future structured context expansion, but 7.2A currently exposes only `query_text`, so the adapter does not infer structured values from natural language.

Key resolution behavior:

- `capacity` chooses direct lookup vs evaluation from the presence of `guest_count` / `attendee_count`
- `space_access` chooses direct lookup vs evaluation from explicit `mode` / `evaluate`
- `technical_inventory` chooses direct inventory vs quantity evaluation from `requested_quantity`
- `technical_capability` chooses direct capability lookup vs requirement evaluation from `requirement_code` or explicit `mode`
- `payment` synthesizes `insufficient_information` when the requested stage is lead-time-dependent but `booking_lead_time_days` is missing
- direct lookup handlers that would otherwise collapse to zero rows on missing required structured inputs synthesize normalized `insufficient_information` items instead of guessing

## Result normalization

Every successful Phase 4 domain result becomes a frozen `NormalizedResultEnvelope`.

The adapter preserves:

- stable identity via `rule_code` where available
- exact identity via `rule_id` and `rule_version` where available
- direct Phase 4 typed fields in `layer_payload`
- direct source-code arrays from the RPC surface
- effective dates and status fields in native identity payloads or layer payloads
- per-domain traceability via `layer_payload.phase_4_domain`
- executed RPC traceability via `layer_payload.rpc_name`

Inventory and other deterministic non-rule rows remain valid Phase 4 items by using native identity payloads even when a `rule_id` is absent.

## Execution-state mapping

Adapter execution-state rules are:

- `not_requested` when `phase_4.required` is false or Phase 4 is absent from required layers
- `success` when at least one domain returns a normalized item, including explicit no-rule or insufficient-information items
- `failed` when every requested domain fails technically
- `no_results` only if Phase 4 was requested, no domain failed, and no handler produced any normalized item

Mixed-domain success and failure remains `success` at the layer level, with safe partial-failure metadata surfaced through:

- `error_category = phase4_partial_domain_failure`
- `safe_error_message` listing the failed domain codes

No new execution enum was added.

## Reasoning-state mapping

Phase 4 rows normalize into the frozen Phase 7 reasoning states:

- `resolved`
- `requires_confirmation`
- `insufficient_information`
- `no_applicable_rule`
- `manual_review_required`

Mapping rules:

- explicit `manual_review_required` flags or statuses map to `manual_review_required`
- explicit `insufficient_information` statuses map to `insufficient_information`
- explicit confirmation flags or statuses map to `requires_confirmation`
- explicit `no_applicable_rule` and `no_applicable_equipment` statuses map to `no_applicable_rule`
- deterministic outcomes such as `insufficient_quantity`, `restricted`, or `does_not_apply` remain `resolved` while preserving the domain-native state in `layer_payload`

## Typed payload preservation

The adapter does not rewrite Phase 4 truth into retrieval-like summaries.

Every normalized result keeps the original Phase 4 typed fields in `layer_payload`, including examples such as:

- `percentage_due`
- `deadline_type`
- `deadline_value`
- `max_guests`
- `capacity_evaluation_status`
- `access_status`
- `support_status`
- `quantity_evaluation_status`
- `arrangement_status`
- `availability_status`

Summary text uses existing Phase 4 `plain_language_explanation` or `conditions_summary` when available.

## Provenance enrichment

The adapter preserves direct RPC provenance first:

- `primary_source_codes`
- `governance_source_codes`
- `supporting_source_codes`

Then it enriches rule-backed items with locator-level provenance from:

- `public.rule_source_links`
- `public.source_registry`

The enrichment adds:

- `source_registry_ids`
- relation-ordered deep source records
- locators derived from `relative_source_path` or `original_filename`
- source type, authority level, lifecycle status, effective date, and notes

The implementation enriches every returned rule-backed Phase 4 item because Phase 4 result sets are small and 7.2C has no later context-selection stage yet.

## Sensitivity default

Every normalized Phase 4 item uses the frozen helper:

- `phase4_default_sensitivity()`

That yields:

- confidentiality = `internal`
- PI status = `unknown`

No schema-derived sensitivity inference was added.

## Error semantics

Technical RPC failures are surfaced safely:

- layer execution becomes `failed` when all requested domains fail
- no fake deterministic items are created on failure
- safe failure metadata names the failed domain(s)
- SQL credentials, raw connection details, and stack internals are not serialized into Phase 7 envelopes

Missing structured parameters are not treated as technical failures. They normalize into `insufficient_information`.

## Multi-domain behavior

The adapter executes every domain listed in `query_plan.phase_4.domains`.

Downstream code can distinguish results by:

- `layer_payload.phase_4_domain`
- `layer_payload.rpc_name`
- stable identity / exact identity

The adapter does not re-route into undeclared domains.
