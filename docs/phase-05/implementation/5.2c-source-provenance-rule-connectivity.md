## Locator and Identity Model

`knowledge_source_objects` models one physical or externally referenced artifact rather than a logical document or governed document version.

Approved `origin_type` values implemented:

- `repository_file`
- `supabase_storage`
- `external_uri`
- `manual_reference`

Origin-specific locator integrity is enforced at the table level:

- `repository_file` requires `repository_relative_path`
- `supabase_storage` requires both `storage_bucket` and `storage_object_key`
- `external_uri` requires `external_uri`
- `manual_reference` requires `manual_reference_key`

The migration also blocks contradictory locator combinations by requiring non-applicable locator fields to remain null for each origin type.

Identity is locator-based, not checksum-defined.

Implemented uniqueness:

- repository file: unique `repository_relative_path`
- Supabase Storage: unique `(storage_bucket, storage_object_key)`
- external URI: unique `external_uri`
- manual reference: unique `manual_reference_key`

`checksum_sha256` is indexed but not globally unique, so two distinct physical source objects may legitimately share identical bytes.

Additional basic integrity includes:

- non-negative `file_size_bytes`
- non-empty text for populated locator and metadata fields

## Version-to-Source Relationship Invariants

`knowledge_document_version_source_objects` models what a source object means to one governed document version.

Implemented fields include:

- document version FK
- source object FK
- source-object role FK
- `source_usage_disposition`
- `is_preferred_extraction_source`
- `is_primary_representation`
- optional notes

Approved `source_usage_disposition` values implemented:

- `eligible_for_extraction`
- `supporting_only`
- `excluded_from_extraction`

Implemented invariants:

- duplicate relationship rows are rejected through a uniqueness constraint on `(document_version_id, source_object_id, source_object_role_id)`
- at most one preferred extraction source is allowed per document version
- preferred extraction requires `source_usage_disposition = 'eligible_for_extraction'`
- at most one primary representation is allowed per document version
- excluded representations can remain linked historically without being extraction-eligible

No rule was added requiring every governed document version to already have a linked physical source object.

## Stable Logical-Rule Relationships

`knowledge_document_version_logical_rules` implements stable conceptual relationships from governed knowledge to `public.logical_rules.rule_code`.

Implemented integrity:

- FK from `rule_code` to `public.logical_rules(rule_code)`
- uniqueness on `(document_version_id, rule_code, relationship_type_id)`
- trigger-enforced requirement that the chosen relationship type has `target_kind = 'logical_rule'`

This allows stable relationships such as:

- `governed_by`
- `explains`
- `operational_context_for`

without collapsing them into exact rule-version history.

## Exact Rule-Version Relationships

`knowledge_document_version_rule_versions` implements exact historical relationships from governed knowledge to `public.rule_catalogue.id`.

Implemented integrity:

- FK from `rule_version_id` to `public.rule_catalogue(id)`
- uniqueness on `(document_version_id, rule_version_id, relationship_type_id)`
- trigger-enforced requirement that the chosen relationship type has `target_kind = 'rule_version'`

This supports exact historical semantics such as:

- `specifically_reflects`
- `historically_explains`
- `superseded_because_rule_changed`

## Preserved Dual Semantics

The implementation explicitly preserves both knowledge-to-rule relationship layers at the same time:

- stable logical-rule connectivity
- exact rule-version connectivity

They are stored in separate relational tables rather than being collapsed into one generic/free-form relationship structure.

Validation proved that one document version can simultaneously:

- link to a stable logical rule
- link to an exact historical version of that same rule

without conflict.
