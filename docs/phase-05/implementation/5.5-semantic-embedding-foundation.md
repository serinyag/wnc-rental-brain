## Embedding Input Contract

Deterministic embedding input is built as:

```text
Document: <document title snapshot>

Section: <heading path or section heading>

Question: <question label, when present>

<body text>
```

Implementation rules:

- `heading_path` is preferred when present
- `section_heading` is used only when `heading_path` is blank
- `question_label` is included only when present
- body text is preserved exactly as stored on the chunk row
- no LLM-generated summaries or Phase 4 rule-table values are injected

Template-library safety:

- `INTERNAL GUIDANCE` labels are preserved
- `CLIENT-FACING TEMPLATE` labels are preserved
- approved chunk boundaries are not re-split for embeddings

Traceability:

- current embedding input text is exposed through `private.current_knowledge_chunk_embedding_inputs`
- current embedding input identity is tracked as `embedding_input_hash`
- hash algorithm used in this task: deterministic MD5 content hash

## Vector Storage Model

Implemented derived embedding table:

- `private.knowledge_embeddings`

Important design choice:

- the vector column is stored as unconstrained `extensions.vector`
- dimension safety is enforced through a trigger against the registered `embedding_dimensions`

Why this approach was selected:

- it keeps the current rollout compatible with one active retrieval-approved family
- it still permits later registry rows for alternate dimensions without pretending mixed-dimension rows can share one indexed search path safely
- the actual semantic search function always resolves one explicit embedding model family before comparing vectors

Current semantic search therefore remains dimension-safe without overcommitting the repository to one permanent provider family.

## Eligibility Logic

- `knowledge_document_corpus_states.is_current = true`

- effective date window valid on the query date
- chunk set status `current`

## Generation Tooling

Created:

- `tools/phase_05_search/semantic_common.py`
- `tools/phase_05_search/generate_embeddings.py`
- `tools/phase_05_search/evaluate_semantic.py`
- `tools/phase_05_search/tests/test_semantic_search.py`

Generation flow implemented in `python3 -m tools.phase_05_search.generate_embeddings`:

1. resolve current-search-eligible chunk inputs
2. resolve or register the embedding model configuration
3. compute configuration fingerprint deterministically
4. detect existing `(chunk_id, input_hash)` coverage for the selected model family
5. skip unchanged rows
6. request missing embeddings from the provider in batches
7. validate returned dimensions
8. insert derived embedding rows
9. report coverage summary

Current provider support in repository tooling:

- `openai`

The registry itself remains provider-agnostic even though the repository client implementation currently supports only OpenAI.

## Semantic Search Function

Created private function:

- `private.search_knowledge_chunks_semantic(p_query_embedding extensions.vector, p_result_limit integer default 10, p_embedding_model_id bigint default null, p_document_code text default null, p_category_code text default null, p_rental_type_code text default null)`

Implemented behavior:

- exact cosine-distance ranking
- explicit vector-dimension validation against the resolved model family
- default resolution to the one active retrieval-approved embedding family
- optional filters already supported by governed metadata:
  - document code
  - primary category code
  - rental type code
- provenance-bearing result shape aligned with the FTS search surface

Search returns:

- governed document identity and version number
- chunk ordinal and headings
- body text
- content hash
- input content hash
- embedding model identity
- cosine distance
- human-readable similarity score
- exact chunk provenance fields

## Security

All semantic infrastructure remains private:

- `private.knowledge_embedding_models` uses RLS and revoked grants
- `private.knowledge_embeddings` uses RLS and revoked grants
- `private.current_knowledge_chunk_embedding_inputs` has revoked direct grants
- `private.search_knowledge_chunks_semantic(...)` execution is revoked from `public`, `anon`, `authenticated`, and `service_role`

No public `api` semantic-search RPC was added.
