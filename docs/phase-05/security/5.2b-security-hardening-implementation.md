## Policy Posture

No client-facing RLS policies were added.

Initial posture is:

- no `anon` policies
- no `authenticated` policies
- no `service_role` policies

RLS is being used here as defense in depth on top of PostgreSQL privilege cleanup.

## Grant Cleanup

### Protected Base Tables

For all 26 protected base tables, ordinary-role privileges were removed for:

- `anon`
- `authenticated`
- `service_role`

This cleanup removed direct table privileges rather than preserving partial ordinary-role access.

### Curated Views Retained

The approved Phase 4 public read surface remains:

- `public.current_*` views only

For all current approved `public.current_*` views:

- `SELECT` was retained for `anon`, `authenticated`, and `service_role`
- redundant `REFERENCES`, `TRIGGER`, and `TRUNCATE` privileges were removed

No view definitions were changed.

## Public RPC EXECUTE Permissions Withdrawn

Public/client execution was withdrawn from the audited Phase 4 rental RPC surface for:

- `anon`
- `authenticated`

The withdrawn surface is:

- `api.get_booking_fee_rule(...)`
- `api.get_payment_rules(...)`
- `api.get_expedited_surcharge_rule(...)`
- `api.get_cancellation_rules(...)`
- `api.get_capacity_rule(...)`
- `api.evaluate_capacity(...)`
- `api.get_space_access_rule(...)`
- `api.evaluate_space_access(...)`
- `api.get_operational_requirements(...)`
- `api.get_catering_supplier_rules(...)`
- `api.get_technical_equipment_inventory(...)`
- `api.evaluate_technical_equipment_quantity(...)`
- `api.get_technical_capability(...)`
- `api.evaluate_technical_requirement(...)`
- `api.get_service_rules(...)`
- `api.get_facilitator_requirements(...)`

Important implementation note:

- revoking from `anon` and `authenticated` alone was not sufficient because PostgreSQL function execute can still arrive through `PUBLIC`
- the final migration therefore revokes from `PUBLIC`, `anon`, and `authenticated`
- explicit `service_role` execute grants from the original Phase 4 migrations remain in place

No function bodies were changed.
No functions were converted to `SECURITY DEFINER`.
No `private` schema access was granted to ordinary roles.

## Service Role Posture

Service-role posture after hardening:

- no direct protected-base-table privileges remain
- curated `public.current_*` view `SELECT` remains
- explicit Phase 4 RPC `EXECUTE` remains
- no RLS policies were added for `service_role`

## Practical Role-Test Results

Local role checks after the migration:

### Direct Phase 4 table

- `SET ROLE anon; SELECT count(*) FROM public.booking_fee_rules`
- result: blocked with `permission denied for table booking_fee_rules`

- `SET ROLE authenticated; SELECT count(*) FROM public.booking_fee_rules`
- result: blocked with `permission denied for table booking_fee_rules`

### Curated Phase 4 view

- `SET ROLE anon; SELECT count(*) FROM public.current_booking_fee_rules WHERE rule_code = 'FEE_STUDIO_1_TO_3_HOUR_BOOKING'`
- result: succeeded and returned `1`

- `SET ROLE authenticated; SELECT count(*) FROM public.current_booking_fee_rules WHERE rule_code = 'FEE_STUDIO_1_TO_3_HOUR_BOOKING'`
- result: succeeded and returned `1`

### Phase 5 table

- `SET ROLE anon; SELECT count(*) FROM public.knowledge_categories`
- result: blocked with `permission denied for table knowledge_categories`

- `SET ROLE authenticated; SELECT count(*) FROM public.knowledge_categories`
- result: blocked with `permission denied for table knowledge_categories`

### Withdrawn RPC

- `SET ROLE anon; SELECT count(*) FROM api.get_booking_fee_rule(...)`
- result: blocked with `permission denied for function get_booking_fee_rule`

- `SET ROLE authenticated; SELECT count(*) FROM api.get_booking_fee_rule(...)`
- result: blocked with `permission denied for function get_booking_fee_rule`

Equivalent local HTTP checks with the anon key:

- `GET /rest/v1/booking_fee_rules?select=rule_id&limit=1`
  - result: `401 permission denied for table booking_fee_rules`
- `GET /rest/v1/current_booking_fee_rules?select=rule_code&rule_code=eq.FEE_STUDIO_1_TO_3_HOUR_BOOKING`
  - result: `200` with the expected row
- `POST /rest/v1/rpc/get_booking_fee_rule` with `Accept-Profile: api`
  - result: `401 permission denied for function get_booking_fee_rule`
