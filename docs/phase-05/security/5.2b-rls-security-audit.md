# Phase 5.2B RLS Security Audit

Date: August 6, 2026

## Executive Summary

This audit reviewed the 26 `public` tables flagged by Supabase Security Advisor after Task 5.2A.

The main repository-specific findings are:

1. The flagged base tables are not currently directly readable by `anon` or `authenticated` through ordinary `SELECT` privileges.
2. Phase 5 private knowledge tables are already private by grants, but not by RLS.
3. Phase 4 `public.current_*` views are the only Phase 4 public read surface that is actually working for `anon` today.
4. Most granted `api.*` functions are not actually callable by `anon` or `authenticated` today.
5. Enabling RLS on the flagged base tables is compatible with the current granted `public.current_*` views in the local stack.
6. RLS does not fix the broken `api.*` function surface. Those functions need a separate architecture decision.

Local proofs collected during this audit:

- `GET /rest/v1/booking_fee_rules?select=rule_id&limit=1` with the local anon key returned `401 permission denied for table booking_fee_rules`.
- `GET /rest/v1/current_booking_fee_rules?select=rule_code&limit=1` with the local anon key returned `200` and data.
- `POST /rest/v1/rpc/get_booking_fee_rule` with `Accept-Profile: api` and the local anon key returned `401 permission denied for schema private`.
- `SET ROLE anon; SELECT count(*) FROM public.current_booking_fee_rules;` succeeded locally.
- `SET ROLE anon; SELECT count(*) FROM api.get_booking_fee_rule(...);` failed locally because the function touches `private`.
- In a local transaction, `ENABLE ROW LEVEL SECURITY` plus temporary `GRANT SELECT` on `public.knowledge_categories` returned `0` rows for `anon` and `authenticated`, but `7` rows for `service_role`.

Conclusion:

- Least-privilege hardening should still enable RLS on all 26 flagged tables.
- Initial policy posture should be no client policies on all 26 flagged tables.
- `service_role` must stay minimally granted, because it bypasses RLS.
- The current `api.*` architecture needs review before any hardening migration claims that Phase 4 public RPC behavior is preserved.

Status:

`PHASE_5_SECURITY_ARCHITECTURE_REVIEW_REQUIRED`

## Current Security Model

Observed local stack facts:

- `supabase/config.toml` exposes `public`, `api`, and `graphql_public` through the API.
- `auto_expose_new_tables` is not enabled in `supabase/config.toml`.
- All 26 flagged tables are owned by `postgres`.
- All granted `public.current_*` views are owned by `postgres`.
- All granted `api.*` functions are owned by `postgres`.
- `anon` and `authenticated` have `USAGE` on `public` and `api`, but not on `private`.
- `service_role` has `USAGE` on `public` and `api`, but not on `private`.
- `service_role` and `postgres` have `rolbypassrls = true`.
- `anon`, `authenticated`, and `service_role` do not currently have direct `SELECT`, `INSERT`, `UPDATE`, or `DELETE` on the 26 flagged base tables.
- Many flagged Phase 4 tables still carry redundant `REFERENCES`, `TRIGGER`, and `TRUNCATE` grants for `anon`, `authenticated`, and `service_role`.
- Phase 5.2A already revoked `anon` and `authenticated` privileges from the new Phase 5 tables, but `service_role` still retains redundant `REFERENCES`, `TRIGGER`, and `TRUNCATE`.

Effective current model:

- Base-table privacy is currently enforced primarily by SQL privileges, not by RLS.
- Curated public read behavior currently comes from granted owner-rights views in `public`.
- Granted `api.*` EXECUTE rights do not guarantee real usability.
- Supabase Security Advisor correctly observes that RLS is disabled, but its “fully exposed” description does not match the current direct-table grant state of this repository.

## Current Grants

### Base Tables

Observed grant pattern on flagged Phase 4 base tables and canonical/provenance tables:

- `anon`: `REFERENCES`, `TRIGGER`, `TRUNCATE`
- `authenticated`: `REFERENCES`, `TRIGGER`, `TRUNCATE`
- `service_role`: `REFERENCES`, `TRIGGER`, `TRUNCATE`
- `postgres`: owner privileges including `SELECT`, `INSERT`, `UPDATE`, `DELETE`

Observed grant pattern on new Phase 5.2A private knowledge tables and `public.logical_rules`:

- `anon`: none
- `authenticated`: none
- `service_role`: `REFERENCES`, `TRIGGER`, `TRUNCATE`
- `postgres`: owner privileges including `SELECT`, `INSERT`, `UPDATE`, `DELETE`

Security meaning:

- The redundant `REFERENCES`, `TRIGGER`, and `TRUNCATE` grants are not the intended read surface and should not survive the hardening migration.
- The absence of direct `SELECT` on the 26 flagged base tables is the current reason direct PostgREST base-table reads fail.

### Views

Every granted `public.current_*` view currently has:

- owner: `postgres`
- security mode: default owner-rights view
- reloptions: empty, so not `security_invoker`
- grants to `anon`, `authenticated`, `service_role`: `SELECT` plus redundant `REFERENCES`, `TRIGGER`, `TRUNCATE`

Only `SELECT` is functionally justified for the intended curated read surface.

### Functions

Every granted `api.*` routine currently has:

- owner: `postgres`
- security mode: `SECURITY INVOKER` default, because `prosecdef = false`
- no explicit `search_path` in `proconfig`
- `EXECUTE` granted to `anon`, `authenticated`, and `service_role`

Those grants are not enough to make all RPCs usable, because invoker functions still need access to everything they touch.

## Phase 4 View/Function Dependency Audit

### Granted `public.current_*` Views

All granted `current_*` views are owner-rights views owned by `postgres`.

Underlying table pattern:

- each view joins its typed Phase 4 rule table to `rule_catalogue`
- most views also aggregate provenance through `rule_source_links` and `source_registry`
- some views also join canonical entities such as `rental_types`, `venue_spaces`, or `technical_equipment_inventory`
- each view limits rows to current active policy based on `status`, `effective_from`, and `effective_until`

Observed behavior with RLS enabled on backing tables:

- local transactional test:
  - `ALTER TABLE booking_fee_rules, rule_catalogue, rule_source_links, source_registry, rental_types ENABLE ROW LEVEL SECURITY`
  - `SET ROLE anon`
  - `SELECT count(*) FROM public.current_booking_fee_rules`
- result: still returned `5` rows

Observed behavior with `FORCE ROW LEVEL SECURITY` added to the same backing tables:

- local transactional test:
  - `ALTER TABLE ... FORCE ROW LEVEL SECURITY`
  - `SET ROLE anon`
  - `SELECT count(*) FROM public.current_booking_fee_rules`
- result: still returned `5` rows

Repository-specific explanation:

- the view owner is `postgres`
- `postgres` has `rolbypassrls = true` in the local stack
- therefore the owner-rights view continues to resolve rows even when the calling role is `anon`

Phase 4 view conclusion:

- Phase 4 `current_*` views can remain the public curated read surface while their backing tables move under RLS.
- This repository should use `ENABLE RLS` on Phase 4 backing tables.
- `FORCE RLS` is not required for the current design and adds no practical value while owner objects remain owned by a BYPASSRLS role.

### Granted `api.*` Functions

The granted RPC surface splits into two categories.

#### Category 1: functions that already fail for `anon`

Functions blocked by `private` schema access:

- `api.get_booking_fee_rule`
- `api.get_expedited_surcharge_rule`
- `api.get_cancellation_rules`

Proofs:

- `SET ROLE anon; SELECT count(*) FROM api.get_booking_fee_rule(...)` failed with `permission denied for schema private`
- `GET /rest/v1/rpc/get_booking_fee_rule` with `Accept-Profile: api` failed with `401 permission denied for schema private`

Functions blocked by direct base-table reads:

- `api.get_payment_rules`
- `api.get_capacity_rule`
- `api.evaluate_capacity`
- `api.get_space_access_rule`
- `api.evaluate_space_access`
- `api.get_operational_requirements`
- `api.get_catering_supplier_rules`
- `api.get_technical_capability`
- `api.evaluate_technical_requirement`
- `api.get_service_rules`
- `api.get_facilitator_requirements`

Proofs:

- each of the above failed locally under `SET ROLE anon`
- failure mode was direct `permission denied for table ...`
- their definitions query the Phase 4 base tables directly rather than reading through `public.current_*`

#### Category 2: functions that are callable today

- `api.get_technical_equipment_inventory`
- `api.evaluate_technical_equipment_quantity`

These functions work because they read from `public.current_technical_equipment_inventory`, which is already a granted owner-rights view.

### Phase 4 Compatibility Decision

Key answer to the Phase 4 question:

> Can Phase 4 base tables be RLS-protected without breaking the intentionally granted `current_*` and `api.*` read surfaces?

Answer:

- `public.current_*` views: yes
- most `api.*` functions: not applicable in the hoped-for sense, because they are already broken for `anon` and `authenticated` today

Therefore:

- enabling RLS on Phase 4 base tables does not break the currently working Phase 4 view surface
- a later hardening change must not claim to preserve public RPC behavior unless the RPC layer is separately redesigned

## Phase 5 Exposure Audit

Approved Phase 5 principle:

> Phase 5 organizational knowledge is server-side/private by default.

Current implementation status:

- direct `anon` read on `public.knowledge_categories` fails today
- direct `anon` read on `public.knowledge_documents` would fail today for the same reason
- `authenticated` is in the same position
- `service_role` also lacks direct `SELECT` today
- no `public.current_*` views or `api.*` functions expose Phase 5.2A tables

Observed result:

- Phase 5 privacy is currently achieved by grants alone
- RLS would strengthen the posture and remove reliance on grants alone
- RLS with no client policies would not break current migrations, seeds, or pgTAP, because those run as `postgres`

Transactional proof:

- `ALTER TABLE public.knowledge_categories ENABLE ROW LEVEL SECURITY`
- temporary `GRANT SELECT ON public.knowledge_categories TO anon, authenticated, service_role`
- `SET ROLE anon; SELECT count(*) FROM public.knowledge_categories` returned `0`
- `SET ROLE authenticated; SELECT count(*) FROM public.knowledge_categories` returned `0`
- `SET ROLE service_role; SELECT count(*) FROM public.knowledge_categories` returned `7`

Meaning:

- no-policy RLS correctly blocks ordinary client roles
- `service_role` bypasses RLS as expected
- separate direct `service_role` table grants should still be treated as a deliberate future decision, not a default

## Distinguishing Grants From RLS

This repository needs all four layers documented separately.

### PostgreSQL Table Privileges

This layer currently does most of the real work.

- no direct `SELECT` on flagged base tables means no direct base-table reads through SQL or PostgREST
- view and function grants only help if the underlying object access model also works

### Supabase/PostgREST Schema Exposure

This layer only exposes schemas and callable objects that the role can actually use.

- `public` and `api` are exposed
- exposed base tables are still blocked if the role lacks direct table privileges
- exposed RPCs still fail if the invoker lacks access to the tables or helper schema they touch

### RLS

RLS should be the defense-in-depth control for every flagged backing table, not a substitute for careful grants.

- RLS protects against accidental future direct grants
- RLS protects against future policy drift where a developer exposes a base table too broadly
- RLS does not remove the need to minimize grants
- RLS does not stop `service_role` or `postgres` when they have BYPASSRLS

### Ownership / Execution Semantics

- owner-rights views matter in this repository
- invoker functions matter in this repository
- `private` schema access matters in this repository

This is why `REVOKE` and `ENABLE RLS` are not interchangeable.

## Recommended Table-by-Table RLS Posture

Recommended baseline:

- all 26 flagged tables: `ENABLE_RLS`
- all 26 flagged tables: no direct `anon` policy
- all 26 flagged tables: no direct `authenticated` policy
- all 26 flagged tables: no direct `service_role` policy needed

Table classes and rationale:

- `PRIVATE_KNOWLEDGE`: Phase 5.2A tables should be server-only by default
- `CURATED_RULE_BACKING_TABLE`: Phase 4 typed tables should be protected backing tables, with public access only through approved curated surfaces
- `CANONICAL_REFERENCE`: `rental_types` and `venue_spaces` are shared reference data, but there is no current direct client-table requirement
- `GOVERNANCE_PROVENANCE`: `source_registry` should remain non-client-readable to avoid provenance leakage
- `INTERNAL_IMPLEMENTATION`: `logical_rules`, `rule_catalogue`, and `rule_source_links` should never become direct client tables

Special reviews:

- `public.logical_rules`: enable RLS; keep server-side only; no client policies; no new grants
- `public.rental_types`: enable RLS; keep as backing/canonical support; no direct client policy unless a real UI need appears later
- `public.venue_spaces`: same recommendation as `rental_types`
- `public.source_registry`: enable RLS; no client policies; treat as provenance-sensitive backing data

## Recommended Policy Posture

Initial policy posture for every flagged table:

- no `anon` policies
- no `authenticated` policies
- no `service_role` policies

Why no policies are enough initially:

- current public Phase 4 read behavior that actually works is view-based, not table-policy-based
- current Phase 5 tables have no approved client UI
- current migrations and pgTAP run as `postgres`
- `service_role` bypasses RLS and does not need a policy if future direct grants are intentionally added later

Project recommendation:

- use `ENABLE RLS`
- do not use `FORCE RLS` in the first hardening migration

Repository-specific reason:

- the design relies on owner-rights curated views
- `FORCE RLS` provides no present benefit in the local owner model
- `FORCE RLS` would be easy to overstate as extra protection while the real public issue is still the broken invoker-RPC layer

## Recommended Grant Changes

Recommended table-grant changes for the later hardening migration:

1. Revoke `REFERENCES`, `TRIGGER`, and `TRUNCATE` from all 26 flagged base tables for `anon`.
2. Revoke `REFERENCES`, `TRIGGER`, and `TRUNCATE` from all 26 flagged base tables for `authenticated`.
3. Revoke `REFERENCES`, `TRIGGER`, and `TRUNCATE` from all 26 flagged base tables for `service_role`.
4. Keep no direct `SELECT`, `INSERT`, `UPDATE`, or `DELETE` grants for `anon` or `authenticated` on the flagged base tables.
5. Do not add direct `service_role` DML grants to the Phase 5 tables yet, because there is no approved app/service workflow requiring them.

Recommended view-grant cleanup:

1. Keep `SELECT` on the approved `public.current_*` views for `anon`, `authenticated`, and `service_role`.
2. Revoke redundant `REFERENCES`, `TRIGGER`, and `TRUNCATE` from those views for the same roles.

Recommended function-grant decision:

- current `EXECUTE` grants on most `api.*` functions are misleading because the functions are not actually callable by `anon` today
- before the hardening migration, choose one of these paths:
  - path A: remove public execute grants from broken RPCs and treat `public.current_*` views as the only approved public Phase 4 surface for now
  - path B: redesign the RPCs so they are intentionally callable, then keep public execute grants

This decision is unresolved and blocks a clean “ready for implementation” closeout.

## Phase 4 Compatibility Risks

Current Phase 4 public compatibility risks are not primarily about RLS.

The real risks are:

1. Most `api.*` functions are currently granted but unusable for public roles.
2. Many `api.*` functions read base tables directly as invoker routines, which is structurally inconsistent with the “curated surface” pattern.
3. Functions that call `private.*` helpers cannot succeed for public roles without either:
   - `private` schema usage access, which should not be granted broadly, or
   - a different function security model

Compatibility-safe observation:

- enabling RLS on Phase 4 backing tables does not break the currently working `current_*` views

Compatibility-risk observation:

- if the project intends public RPCs to stay part of the Phase 4 read contract, those RPCs need redesign before the hardening migration

## Phase 5 Security Recommendations

Recommended baseline for Phase 5 tables:

- enable RLS on every new Phase 5.2A table
- keep no client policies
- keep no direct client grants
- keep no direct `service_role` data grants until a real server-side use case is approved

This matches the stated Phase 5 principle:

> Phase 5 organizational knowledge is server-side/private by default.

## Required pgTAP Security Tests

The later implementation should add role-behavior tests, not just metadata checks.

Required tests:

1. `anon` cannot directly `SELECT` from each flagged Phase 5 table.
2. `authenticated` cannot directly `SELECT` from each flagged Phase 5 table.
3. `anon` cannot directly `SELECT` from Phase 4 backing tables.
4. `authenticated` cannot directly `SELECT` from Phase 4 backing tables.
5. `anon` can still `SELECT` from approved `public.current_*` views.
6. `authenticated` can still `SELECT` from approved `public.current_*` views.
7. `service_role` can still use the surfaces intentionally left usable after the hardening decision.
8. direct base-table PostgREST access remains blocked for ordinary client roles.
9. deterministic Phase 4 result rows returned by approved curated surfaces remain unchanged after hardening.
10. `source_registry`, `logical_rules`, `rental_types`, and `venue_spaces` follow the chosen least-privilege posture.
11. if public RPCs remain granted, pgTAP must prove they are actually callable and return the same deterministic results.
12. if public RPCs are intentionally withdrawn, pgTAP must prove execute is revoked from the withdrawn set.

## Proposed Hardening Migration Scope

Proposed migration scope after review:

1. enable RLS on all 26 flagged tables
2. add no client policies on those 26 tables
3. revoke redundant non-data grants from flagged base tables
4. revoke redundant non-`SELECT` grants from approved `public.current_*` views
5. preserve the current working public view surface
6. separately resolve the public RPC question before changing `api.*` exposure

Do not combine the RPC redesign with the first pure table-hardening step unless the implementation intentionally bundles both and adds role-based regression tests.

## Human Decisions Required

1. Should the public Phase 4 read contract be “views only for now,” or should the `api.*` RPC layer be a supported public surface?
2. If the RPC layer should remain public, should it be redesigned around:
   - owner-rights or security-definer RPCs with explicit `search_path`, or
   - a different curated-surface architecture?
3. Should `service_role` receive any direct Phase 5 table DML grants before an app/service layer exists?
4. Should redundant `TRIGGER`, `TRUNCATE`, and `REFERENCES` grants be fully removed from the granted public views as part of the same hardening migration?

These are architecture choices, not just migration toggles.

## Security Advisor Outcome

If the project enables RLS on all 26 flagged tables, the critical RLS advisories should stop flagging those tables for “RLS disabled.”

However:

- the advisory currently overstates direct exposure relative to the actual grant state
- a green dashboard alone would not prove the access architecture is correct
- the public RPC layer would still need review even after the RLS warnings disappear

Therefore the hardening goal is:

- eliminate the RLS-disabled advisories by enabling RLS on all flagged tables
- keep grant minimization in place
- explicitly resolve the public RPC story instead of assuming the dashboard result means the repository is secure and coherent
