# Phase 6.2B Historical Case Evidence & Provenance Foundation

Date: August 7, 2026

## Summary

Phase 6.2B implements the governed evidence/provenance layer for Phase 6 historical cases.

It adds:

- a Phase-6-specific evidence-role lookup
- version-scoped associations from `historical_case_versions` to reusable `knowledge_source_objects`
- independent evidence-level confidentiality
- association-level evidence strength
- required human-readable source locators
- governed support-dimension metadata
- immutability enforcement once the parent case version leaves `draft`

This task intentionally stops before structured precedent content, Phase 4/5 connectivity, ingestion, or retrieval.

## Artifact Reuse

### Why `public.knowledge_source_objects` is reused

`public.knowledge_source_objects` already provides the generic artifact identity Phase 6 needs:

- repository-file identity
- Supabase Storage identity
- external URI identity
- manual reference identity
- optional `source_registry` bridge
- filename, MIME type, checksum, file size
- artifact-level PI tri-state

Phase 6.2B therefore reuses it directly for artifact identity and avoids building a duplicate artifact registry.

### Why `public.knowledge_document_version_source_objects` is not reused

`public.knowledge_document_version_source_objects` answers a Phase 5 question:

- how one source object functions for one governed knowledge document version

Phase 6 instead needs to answer:

- how one source object functions as evidence for one governed historical case version

Those semantics are different. Reusing the Phase 5 association table would overload document-representation meaning into historical-evidence meaning.

## Evidence Role Semantics

The deferred naming question is resolved in favor of:

- `public.historical_case_evidence_roles`

Reason:

- `knowledge_source_objects` already names the artifact layer
- the new lookup describes the artifact's evidentiary role for one case version
- `evidence` is semantically clearer than `source` at the association layer

Implemented role codes:

- `curated_case_library_source`
  - retrospective curated case-library input, not equivalent to original contemporaneous raw evidence
- `primary_supporting_evidence`
  - strongest direct supporting artifact for the governed reconstruction
- `secondary_supporting_evidence`
  - corroborating or narrower supporting artifact
- `context_only_support`
  - contextual background retained without treating it as direct primary evidence

Lookup columns:

- `role_code`
- `display_name`
- `description`
- `sort_order`
- `is_active`
- `created_at`
- `updated_at`

## Provenance Model

### Core association

`public.historical_case_version_source_objects` is the governed relationship between:

- one `historical_case_version`
- one `knowledge_source_object`
- one `historical_case_evidence_role`

This keeps provenance version-scoped, which matches the Phase 6 immutable-snapshot model.

### Cardinality behavior

The model supports:

- one source object -> many historical case versions
- one historical case version -> many source objects
- one historical case version -> same source object multiple times when the locator differs

That last capability matters because a single artifact can support multiple distinct sections or claims inside the same governed case reconstruction.

### Columns on `historical_case_version_source_objects`

- `historical_case_version_id`
- `source_object_id`
- `evidence_role_id`
- `confidentiality_level_id`
- `evidence_strength`
- `source_locator`
- `supported_claim_dimensions`
- `relationship_notes`
- `created_at`
- `updated_at`

### Source locator

`source_locator` is required and human-readable.

It is intentionally lightweight and does not attempt coordinate-heavy document geometry.

Typical intended future values include:

- section headings
- page or paragraph references
- named case subsections in a shared historical library

Uniqueness is enforced on a normalized locator using:

- `private.normalize_historical_case_source_locator(text)`

This trims, lowercases, and collapses whitespace before uniqueness comparison.

### Evidence strength

Association-level `evidence_strength` is implemented with:

- `strong`
- `moderate`
- `limited`

This is separate from `historical_case_versions.evidence_strength`.

Difference:

- case-version `evidence_strength` summarizes the whole reconstruction
- association `evidence_strength` describes the contribution of one artifact

### Support metadata

The model implements queryable support dimensions through:

- `supported_claim_dimensions text[]`

Allowed values:

- `identity`
- `date`
- `responsibility`
- `decision`
- `lesson`
- `context`

Validation rules:

- array must be present
- array must not be empty
- values must come from the approved vocabulary
- values must not repeat

This keeps support coverage clearer than freeform notes alone, without introducing per-claim boolean sprawl or statement-level evidence links prematurely.

### Notes

`relationship_notes` remains optional and is intended for concise governed provenance commentary such as:

- retrospective curated narrative only
- contemporaneous evidence
- supports identity but not exact date
- context-only use

## Constraints, Indexes, and Security

### Key constraints

On `historical_case_evidence_roles`:

- unique `role_code`
- non-empty `role_code`
- non-empty `display_name`
- non-empty `description`
- non-negative `sort_order`

On `historical_case_version_source_objects`:

- valid FK to `historical_case_versions`
- valid FK to `knowledge_source_objects`
- valid FK to `historical_case_evidence_roles`
- valid FK to `knowledge_confidentiality_levels`
- `evidence_strength` limited to `strong`, `moderate`, `limited`
- non-empty `source_locator`
- validated `supported_claim_dimensions`
- non-empty `relationship_notes` when present

### Indexes

- `historical_case_version_source_objects_unique_idx`
  - unique across:
    - `historical_case_version_id`
    - `source_object_id`
    - `evidence_role_id`
    - normalized `source_locator`
- `historical_case_version_source_objects_source_object_idx`
  - supports reverse source-to-case lookups

### RLS and grants

Both new tables are private by default:

- RLS enabled on `public.historical_case_evidence_roles`
- RLS enabled on `public.historical_case_version_source_objects`
- all direct privileges revoked from `public`, `anon`, `authenticated`, and `service_role`

This preserves the existing Phase 5 / Phase 6 security posture and avoids exposing provenance or evidence to client-side access.

## Confidentiality

Evidence associations carry their own:

- `confidentiality_level_id`

This reuses `public.knowledge_confidentiality_levels` and intentionally does not create a separate evidence taxonomy.

Why this matters:

- curated case version confidentiality belongs to the governed narrative layer
- `knowledge_source_objects` remain generic artifact identity only
- one artifact can therefore be reused without forcing one shared confidentiality meaning everywhere

The model allows:

- case version = `internal`
- linked evidence association = `restricted`

Artifact-level PI remains on `knowledge_source_objects`.

The evidence association does not duplicate PI status, which preserves the intended separation:

- curated case version has its own PI status from 6.2A
- source object has artifact-level PI status from Phase 5
- evidence association has independent confidentiality

## Immutability

Evidence associations are part of the governed historical snapshot.

This is enforced by:

- `private.enforce_historical_case_version_source_object_editability()`

Behavior:

- if the parent case version is `draft`
  - evidence associations may be inserted, updated, and deleted
- if the parent case version is `active`, `superseded`, or `retired`
  - evidence associations may not be inserted
  - evidence associations may not be updated
  - evidence associations may not be deleted

Therefore:

- active governed provenance cannot be silently rewritten
- newly discovered evidence belongs on a new draft/superseding case version
- provenance remains part of the immutable version snapshot rather than a mutable sidecar
