# Phase 6.2A Historical Case Core Governance Foundation

Date: August 7, 2026

## Summary

Phase 6.2A implements the minimum governed Phase 6 foundation required by the approved architecture:

- stable historical case identity
- case alias support
- immutable governed historical case versions
- lifecycle and supersession enforcement
- temporal uncertainty representation
- qualitative precedent/evidence metadata
- curated-case confidentiality and PI classification
- case-level historical-value summary flag
- private-by-default security posture

This task intentionally stops before evidence association, structured precedent statements, Phase 4 or Phase 5 connectivity, ingestion, or retrieval.

## Implemented Objects

### `public.historical_cases`

Purpose:

- one stable historical precedent identity per case

Columns:

- `id bigint generated by default as identity primary key`
- `case_code text not null unique`
- `canonical_title text not null`
- `created_at timestamptz not null default timezone('utc', now())`
- `updated_at timestamptz not null default timezone('utc', now())`

Constraints:

- non-empty `case_code`
- `case_code` format check: `^HC-[0-9]{3,}$`
- non-empty `canonical_title`

Triggers:

- `trg_historical_cases_touch_updated_at`
  - uses `private.touch_updated_at()`

### `public.historical_case_aliases`

Purpose:

- alternate labels attached to one stable historical case

Columns:

- `id bigint generated by default as identity primary key`
- `historical_case_id bigint not null references public.historical_cases(id) on delete cascade`
- `alias_text text not null`
- `alias_type text`
- `created_at timestamptz not null default timezone('utc', now())`
- `updated_at timestamptz not null default timezone('utc', now())`

Constraints:

- non-empty `alias_text`
- optional `alias_type` constrained to:
  - `client`
  - `brand`
  - `event`
  - `person`
  - `shorthand`
  - `other`
- non-empty `alias_type` when present

Normalization and index:

- `private.normalize_historical_case_alias_text(text)`
  - lowercases, trims, and collapses internal whitespace
- `historical_case_aliases_case_alias_unique_idx`
  - unique per case on normalized alias text

Triggers:

- `trg_historical_case_aliases_touch_updated_at`
  - uses `private.touch_updated_at()`

### `public.historical_case_versions`

Purpose:

- one governed reconstruction snapshot for one historical case

Columns:

- identity and lineage:
  - `id`
  - `historical_case_id`
  - `version_number`
  - `supersedes_version_id`
- governance:
  - `governance_status`
  - `activated_at`
- precedent characterization:
  - `precedent_availability`
  - `precedent_type`
  - `evidence_strength`
  - `historical_event_status`
- temporal model:
  - `temporal_precision`
  - `event_date_start`
  - `event_date_end`
  - `temporal_note`
- governed content:
  - `curated_narrative`
  - `contains_historical_value_only_content`
- security metadata:
  - `confidentiality_level_id`
  - `personal_information_status`
  - `personal_information_notes`
- audit:
  - `created_at`
  - `updated_at`

Constraints:

- positive `version_number`
- `unique (historical_case_id, version_number)`
- governance status limited to:
  - `draft`
  - `active`
  - `superseded`
  - `retired`
- precedent availability limited to:
  - `active`
  - `limited`
  - `held`
  - `archived`
- precedent type limited to:
  - `full_case`
  - `limited_precedent`
  - `cautionary_precedent`
- evidence strength limited to:
  - `strong`
  - `moderate`
  - `limited`
- historical event status limited to:
  - `completed`
  - `cancelled`
  - `postponed`
  - `planning_only`
  - `partial_or_unclear`
- temporal precision limited to:
  - `exact`
  - `approximate`
  - `month`
  - `year`
  - `unknown`
- valid date ordering when both bounds exist
- non-empty `temporal_note` when present
- non-empty `curated_narrative`
- `personal_information_status` limited to:
  - `yes`
  - `no`
  - `unknown`
- non-empty `personal_information_notes` when present
- temporal precision consistency:
  - `unknown` requires no bounds
  - `exact` requires one exact day (`event_date_start = event_date_end`)
  - `approximate` requires bounded dates
  - `month` requires first-day and last-day bounds for one month
  - `year` requires January 1 through December 31 bounds for one year

Indexes:

- `historical_case_versions_one_active_version_per_case_idx`
  - partial unique index on `historical_case_id`
  - applies only where `governance_status = 'active'`

Triggers and functions:

- `private.validate_historical_case_version_supersession()`
  - no self-supersession
  - superseded target must belong to the same stable case
  - superseding version number must increase
- `private.enforce_historical_case_version_lifecycle()`
  - drafts may remain draft, become active, or be retired
  - active versions may remain active, become superseded, or be retired
  - superseded versions cannot become draft or active again
  - retired versions are terminal
  - non-draft versions cannot be materially rewritten in place
  - `activated_at` is auto-set when a version becomes active
  - drafts cannot carry `activated_at`
  - superseded versions must retain `activated_at`
- `trg_historical_case_versions_touch_updated_at`
- `trg_validate_historical_case_version_supersession`
- `trg_enforce_historical_case_version_lifecycle`

## Governance Behavior

### Stable case versus case version

- `historical_cases` holds durable identity only.
- `historical_case_versions` holds the governed reconstruction snapshot.
- Narrative, temporal interpretation, precedent metadata, confidentiality, and PI classification all belong to the version layer, not the stable identity row.

### Draft editability

- draft versions are editable
- draft rows can change governed fields before activation

### Activation

- active versions represent the currently governed historical reconstruction for a case
- activation is recorded with `activated_at`
- only one active version may exist per stable case

### Supersession

- a new version may supersede a prior version from the same stable case
- supersession is version-to-version, not case-to-case
- the superseding version stores `supersedes_version_id`

### One-active-version rule

- enforced by a partial unique index
- application code is not trusted as the only enforcement layer

### Immutability

- once a version leaves `draft`, governed content cannot be materially rewritten
- historical corrections require a new version
- superseded and retired versions remain preserved instead of being overwritten

## Temporal Model

Phase 6.2A implements temporal uncertainty with:

- `temporal_precision`
- `event_date_start`
- `event_date_end`
- optional `temporal_note`

Representation:

- `exact`
  - exact known day
  - `event_date_start = event_date_end`
- `approximate`
  - bounded approximate range
  - start and end are both required
- `month`
  - first and last day of a specific month
- `year`
  - January 1 through December 31 of a specific year
- `unknown`
  - no date bounds stored

This avoids fake placeholder dates such as `1900-01-01` while still allowing later exact evidence to fit the same schema.

## Security

Curated-case security metadata implemented at this layer:

- `confidentiality_level_id bigint not null references public.knowledge_confidentiality_levels(id)`
- `personal_information_status text not null`
- `personal_information_notes text`

Security posture:

- `historical_cases`, `historical_case_aliases`, and `historical_case_versions` all have RLS enabled
- all direct table privileges are revoked from `anon`, `authenticated`, and `service_role`
- no public read surface is created in this task

This preserves the Phase 5 private-by-default pattern and satisfies:

- `P6-INV-001 — Authority Separation`
- `P6-INV-008 — Confidentiality Separation`
- `P6-INV-009 — Version Supersession`
- `P6-INV-010 — Statement-Level Contamination Control`

Note:

- only the case-level summary flag is implemented here
- statement-level contamination controls remain intentionally deferred

## Boundary Check

This implementation preserves the intended authority boundary:

`Phase 4 deterministic rules` -> `Phase 5 governed current knowledge` -> `Phase 6 historical precedent`

Nothing in 6.2A allows a historical case to:

- define a current rule
- replace a Phase 4 value
- override Phase 5 knowledge
- enter the Phase 5 current-knowledge retrieval surface
