## Topic Design

### Why Phase 6 uses its own topic vocabulary

Phase 6 topics classify historical precedent.

They do not classify:

- current deterministic rules
- current governed knowledge documents
- generated or free-form tags

This preserves:

- `P6-INV-001 — Authority Separation`
- `P6-INV-006 — Derived Artifact Boundary`
- `P6-INV-007 — Retrieval Role`

### Why Phase 5 `knowledge_tags` is not reused semantically

There is no implemented Phase 5 `knowledge_tags` table in the current schema; Phase 5 explicitly deferred generic tags.

Even if a future Phase 5 tag table exists, the architecture decision still holds:

- Phase 5 tags would classify current governed knowledge
- Phase 6 precedent topics classify historical precedent

For that reason, 6.2C creates `public.historical_precedent_topics` as a separate controlled lookup rather than overloading current-knowledge semantics into the historical layer.

### Topic table design

`public.historical_precedent_topics` uses the same broad lookup conventions seen elsewhere in the repo:

- surrogate `id`
- stable machine-readable `topic_code`
- `display_name`
- `description`
- `sort_order`
- `is_active`
- `created_at`
- `updated_at`

Constraints:

- unique `topic_code`
- non-empty `topic_code`
- non-empty `display_name`
- non-empty `description`
- non-negative `sort_order`

### Normalization decisions

The corpus matrix provided a broader candidate set. 6.2C intentionally normalized several overlaps:

- `responsibility split` -> `responsibility_boundaries`
  - renamed to better reflect governance boundary-setting, not just one structural split pattern
- `catering fit` + `supplier coordination` -> `catering_supplier_coordination`
  - merged because the audited corpus treated these concerns together more often than independently
- `build-up` + `setup access` + `production access` -> `production_access`
  - merged because the recurring pattern was access-window and staging-boundary precedent rather than three consistently separable governed categories
- `unusual production materials` + `cleanup` + `damage` -> `materials_cleanup_damage`
  - merged because the corpus treated these as one recurring risk cluster around residue, restoration, and damage handling
- `brand restrictions` + `collaboration pressure` -> `branding_restrictions`
  - merged because the narrower collaboration-pressure examples still revolved around brand-use and brand-boundary precedent
- `permit and compliance review` -> `permits_compliance`
  - renamed into a shorter stable code while preserving the same semantic scope

Topics kept separate on purpose:

- `storage` and `offsite_storage`
  - retained separately because off-site storage meaningfully differs from ordinary use of the venue storage room
- `technical_assessment` and `electrical_load`
  - retained separately because electrical load is a narrower but operationally important technical precedent theme
- `production_access` and `overtime`
  - retained separately because access-window precedent and overtime precedent are often related, but not identical

## Association Design

### `public.historical_case_version_topics`

Purpose:

- many-to-many relationship between one governed historical case version and one governed precedent topic

Columns:

- `historical_case_version_id`
- `topic_id`
- `topic_relevance`
- `created_at`
- `updated_at`

Constraints:

- valid FK to `public.historical_case_versions`
- valid FK to `public.historical_precedent_topics`
- `topic_relevance` limited to `primary` or `secondary`
- unique per `(historical_case_version_id, topic_id)`

Rationale:

- topic relevance is useful for historical case-topic classification because the corpus audit already distinguished primary versus secondary relevance in similar analytical work

### `public.historical_case_version_rental_types`

Purpose:

- many-to-many relationship between one governed historical case version and canonical `public.rental_types`

Columns:

- `historical_case_version_id`
- `rental_type_id`
- `created_at`
- `updated_at`

Constraints:

- valid FK to `public.historical_case_versions`
- valid FK to `public.rental_types`
- unique per `(historical_case_version_id, rental_type_id)`

No separate Phase 6 rental-type lookup is created.

### `public.historical_case_version_spaces`

Purpose:

- many-to-many relationship between one governed historical case version and canonical `public.venue_spaces`

Columns:

- `historical_case_version_id`
- `venue_space_id`
- `created_at`
- `updated_at`

Constraints:

- valid FK to `public.historical_case_versions`
- valid FK to `public.venue_spaces`
- unique per `(historical_case_version_id, venue_space_id)`

No separate Phase 6 space lookup is created.

## Rental Type Reuse

Phase 6 reuses `public.rental_types` directly.

That means:

- case classification adapts to the canonical rental-type vocabulary
- no duplicate historical rental-type taxonomy is introduced
- a case may have zero, one, or multiple canonical rental-type links

Important caveat:

- this association means the case involved or materially maps to the canonical rental type
- it does not mean the historical case defines that rental type or governs its current policy meaning

## Venue Space Reuse

Phase 6 reuses `public.venue_spaces` directly.

That means:

- case classification adapts to the canonical space vocabulary
- no duplicate historical space taxonomy is introduced
- a case may have zero, one, or multiple canonical space links

Historical scope caveat:

- canonical space links are approximation/classification aids
- they do not rewrite historical narrative detail
- if a historical configuration has no good canonical equivalent, the link can remain absent and the narrative can preserve the historical nuance later

## Governance and Immutability

All 6.2C associations are version-scoped and derive editability from:

- `historical_case_versions.governance_status`

This reuses the Phase 6.2A lifecycle boundary rather than inventing a separate activation model.

Implemented helper:

- `private.enforce_historical_case_version_classification_editability()`

Behavior:

- if parent case version is `draft`
  - topic links may be inserted, updated, and deleted
  - rental-type links may be inserted, updated, and deleted
  - space links may be inserted, updated, and deleted
- if parent case version is `active`, `superseded`, or `retired`
  - inserts are blocked
  - updates are blocked
  - deletes are blocked

This preserves:

- `P6-INV-009 — Version Supersession`

Any classification change discovered after activation must go into a new draft/superseding case version.

## Security

RLS is enabled on:

- `public.historical_precedent_topics`
- `public.historical_case_version_topics`
- `public.historical_case_version_rental_types`
- `public.historical_case_version_spaces`

Direct privileges are revoked from:

- `public`
- `anon`
- `authenticated`
- `service_role`

This keeps classification private and server-side by default, consistent with 6.2A and 6.2B.
