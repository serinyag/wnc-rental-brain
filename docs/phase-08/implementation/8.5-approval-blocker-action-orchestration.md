# Phase 8.5 - Approval, Blocker & Action Orchestration

Date completed: 2026-08-13

## Scope

Phase 8.5 implements the deterministic workflow orchestration layer between structured case state and future execution runtime.

Implemented:

- orchestration input, plan, and result contracts
- stable context builder `build_workflow_orchestration_context(...)`
- stable read-only evaluation entry point `evaluate_workflow_orchestration(...)`
- stable apply entry point `apply_workflow_orchestration_plan(...)`
- stable reconciliation entry point `reconcile_workflow_orchestration(...)`
- deterministic approval boundary `apply_approval_decision(...)`
- deterministic proposed-change boundary `accept_proposed_case_change(...)`
- canonical fact mutation boundary `apply_case_fact_mutation(...)`
- semantic blocker, approval, and action idempotency
- stale-action supersession and artifact freshness packaging
- SQL identity guards for open semantic blockers and approvals
- focused Python and DB regression coverage

Explicitly not implemented:

- external action execution
- lifecycle transitions
- outbound communication sending
- live follow-up scheduler runtime
- proposal or agreement regeneration
- agents, UI, or deployment
- Supabase-backed orchestration repository runtime

## Orchestration Architecture

Phase 8.5 follows an explicit evaluate-then-apply architecture:

```text
WorkflowOrchestrationCaseSnapshot
-> WorkflowOrchestrationContext
-> WorkflowOrchestrationPlan
-> WorkflowOrchestrationResult
```

This preserves the required separation between:

- read-only orchestration evaluation
- mutation application
- future execution runtime
- lifecycle transition evaluation

## Contract Layer Added

`tools/phase_08_workflow/orchestration_types.py` now defines:

- orchestration contract version and label
- deterministic failure taxonomy
- `WorkflowOrchestrationContext`
- `WorkflowOrchestrationPlan`
- `WorkflowOrchestrationResult`
- blocker, approval, action, requirement, and artifact plan-change contracts
- approval, proposed-change, and case-fact mutation input and result contracts

Key contract invariants:

- orchestration context is case-scoped and revision-scoped
- workflow actions must use canonical Phase 8 action types
- approval posture is a closed application-controlled set
- all plan changes require structured ids or references
- payloads must remain JSON-compatible and bounded

## Repository Layer Added

`tools/phase_08_workflow/orchestration_repository.py` adds:

- `WorkflowOrchestrationCaseSnapshot`
- `WorkflowOrchestrationRepositoryProtocol`
- `InMemoryWorkflowOrchestrationRepository`

This layer keeps runtime persistence narrow:

- load one case snapshot with all orchestration-relevant records
- create or resolve blockers
- create or decide approvals
- create or supersede workflow actions
- create requirements
- activate or reject case decisions
- resolve proposed changes
- mutate canonical case facts through one boundary
- mark artifacts stale or refresh-required
- append workflow events

No Supabase-backed orchestration repository is implemented in Phase 8.5.

## Blocker Semantics

Blockers are created only from deterministic structured state:

- open client or internal questions
- insufficient current authority
- confirmation-required reasoning posture
- case-decision approval requirements
- same-scope active case-decision conflicts
- material or fundamental proposed changes

Semantic blocker identity is application-controlled through:

- case id
- blocker meaning
- `resolution_reference = semantic:...`

SQL now adds unique guards for open semantic blockers.

## Approval Semantics

Approvals are created deterministically for:

- approval-required case decisions
- approval-required proposed case changes

Risk posture remains application-controlled:

- `automatic_allowed`
- `approval_required`
- `human_only`
- `blocked`

`apply_approval_decision(...)` now prevalidates invalid-target and same-scope-conflict paths before deciding the approval row so those paths fail closed without partial approval mutation.

## CaseDecision Activation

Approved case-decision activation now:

- requires explicit approval input
- checks expected case revision
- requires proposed or pending-approval decision state
- fails closed on same-scope active conflict
- activates only case-scoped effective truth
- increments case revision
- marks dependent artifacts stale or refresh-required
- supersedes stale actions derived from older case revisions

Phase 4 baseline references remain preserved and unchanged.

## Change Resolution

Proposed changes now support:

- deterministic review blockers
- approval creation when policy requires it
- explicit accept or reject resolution
- canonical fact mutation only through `apply_case_fact_mutation(...)`
- schedule mutation only through the same narrow boundary
- exact-once case revision increment for accepted material truth changes

## Action Planner

Phase 8.5 uses only frozen action taxonomy codes:

- `REQUEST_CLIENT_INFORMATION`
- `CREATE_INTERNAL_TASK_ITEM`
- `ESCALATE_COMPLIANCE_REVIEW`
- `MARK_ARTIFACT_REFRESH_REQUIRED`
- `SCHEDULE_FOLLOW_UP_REVIEW`

Payload validation is enforced per action type.

No generic agent-style action planner exists.

## Requirement Creation

Governed Phase 7 requirement-candidate mappings currently support:

- permit review
- sound or noise compliance review
- insurance confirmation review

Requirement creation remains deterministic and requirement satisfaction is not auto-inferred from Phase 7 existence alone.

## Idempotency And Supersession

Semantic idempotency is implemented through:

- semantic blocker keys
- semantic approval keys
- action `idempotency_key`
- plan fingerprinting

Obsolete managed actions are superseded when:

- questions resolve
- case revision advances
- older unexecuted actions no longer match current workflow truth

## Concurrency, Atomicity, And Audit

Concurrency protection exists for:

- case-decision activation
- proposed-change acceptance
- canonical fact mutation

through expected case revision checks.

However, Phase 8.5 still has three material gaps:

- orchestration-plan apply is not transaction-backed
- no Supabase RPC or DB helper guarantees atomic multi-record commit
- audit event coverage is incomplete for every material mutation type

These are the main reasons readiness remains blocked.

## Limitations

Accepted for this hard stop:

- no external execution runtime
- no lifecycle mutation
- no follow-up scheduler
- no document regeneration
- no UI or provider adapters

Not accepted for readiness yet:

- missing Supabase orchestration repository
- missing transactional apply surface
- incomplete material-mutation audit coverage
- workflow-action approval targets not yet converted into action-state mutation

## Hard-Stop Outcome

Phase 8.5 ends with a deterministic orchestration rule layer that is adequate for local evaluation and integration testing, but not yet ready for Phase 8 execution and follow-up runtime.
