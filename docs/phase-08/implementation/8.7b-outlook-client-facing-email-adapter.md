# Phase 8.7B - Outlook Client-Facing Email Adapter

Date completed: 2026-08-13

## Scope

Phase 8.7B adds the first client-facing outbound email adapter behind the existing Phase 8.6 execution runtime:

- provider implemented: Microsoft Outlook via Microsoft Graph
- rollout surface: governed outbound new-message execution only
- execution boundary preserved: `WorkflowAction -> execution_runtime -> ExecutionAttempt -> adapter -> NormalizedExecutionResult`

Explicitly not implemented:

- inbound Outlook ingestion
- mailbox polling, webhooks, delta queries, or subscriptions
- reply execution
- reply-all
- attachments
- calendar or payment adapters
- execution-time LLM rewriting
- direct agent-to-Outlook sends

## Inspection Conclusions

Inspection established the following:

- the Phase 8.6 adapter interface was already stable
- email-oriented action types already existed, but only `REQUEST_CLIENT_INFORMATION` had a thin executable payload shape
- no canonical persisted client email-address model was present in the inspected Phase 8 surfaces
- no trustworthy persisted Outlook/Graph source message identity was proven for safe reply execution
- the generic `ExecutionAttempt.external_reference` field already supported persisted provider identity on failed, retryable, ambiguous, and successful outcomes
- the runtime already had a provider-neutral ambiguous-outcome posture
- the repository already had conflict protection for successful external references

Implementation consequence:

- keep Outlook narrow
- require explicit structured recipient content
- support new outbound message only
- defer reply execution until exact governed source-message identity exists end-to-end
- avoid a migration because the existing generic execution-attempt model already safely carries provider message identity

## Selected Graph Strategy

Selected send pattern:

- application-permission OAuth client credentials
- explicitly configured sender mailbox
- draft-first send path
- immutable Outlook IDs requested through `Prefer: IdType="ImmutableId"`

Chosen Graph flow:

1. acquire application token
2. create draft at `/users/{mailbox}/messages`
3. persist immutable message identity through `ExecutionAttempt.external_reference`
4. send the exact draft at `/users/{mailbox}/messages/{id}/send`
5. perform one bounded verification read of the same message identity

Why this pattern was selected:

- it preserves one semantic action -> one provider message identity
- it is safer than direct `sendMail` for duplicate-send prevention
- it allows retries to reuse an existing provider message identity
- it prevents blind creation of a second provider draft during retry

## Auth And Mailbox Model

Selected auth mode:

- Microsoft identity OAuth 2.0 client credentials

Selected configuration:

- `MICROSOFT_TENANT_ID`
- `MICROSOFT_CLIENT_ID`
- `MICROSOFT_CLIENT_SECRET`
- `OUTLOOK_SENDER_MAILBOX`
- `MICROSOFT_GRAPH_BASE_URL`
- `MICROSOFT_AUTHORITY_BASE_URL`
- `OUTLOOK_TIMEOUT_SECONDS`

Selected mailbox model:

- one explicitly configured sender mailbox
- no `/me` usage
- no personal-account assumption
- no multi-mailbox mailbox discovery

Operational permission posture documented for this phase:

- `Mail.ReadWrite` application permission is required to create drafts
- `Mail.Send` application permission is required to send the draft

## Action Contract

Phase 8.7B does not introduce a new workflow authority system.

It expects already-governed structured action content inside `WorkflowAction.structured_payload`.

Supported executable Outlook fields:

- `recipient_email`
- `recipient_name`
- `recipient_reference`
- `subject`
- `body`
- `body_type`
- `message_mode`

Required Phase 8.7B values:

- one explicit primary recipient
- `message_mode = "new"`
- `body_type = "text"` or `body_type = "html"`

Rejected in this phase:

- reply mode
- `source_message_reference`
- multi-recipient `to` lists
- `cc`
- `bcc`
- attachments

## Agent Boundary

The agent may draft content before governance, but execution-time behavior is deterministic only.

Execution-time LLM calls:

- `0`

The adapter never:

- rewrites subject lines
- rewrites message bodies
- infers recipients
- infers reply targets
- changes business truth
- changes approval posture

## Recipient Safety

Recipient enforcement in 8.7B is intentionally narrow:

- recipient must be explicit in structured payload
- recipient is validated syntactically
- recipient is never inferred from body text
- recipient is never inferred from historical email context
- recipient is never inferred from Phase 6 precedent
- extra recipient surfaces are rejected

Because no canonical Phase 8 contact-email authority surface was found during inspection, 8.7B deliberately does not attempt to build one inside the adapter.

## Content Immutability

The adapter preserves the exact governed message content except for deterministic provider formatting:

- Graph `body.contentType`
- Graph `body.content`
- recipient serialization

The adapter does not:

- add promises
- add prices
- add dates
- add terms
- generate new subject text
- improvise missing content

## Idempotency And Draft Identity

The key new safety behavior in 8.7B is draft identity reuse across retries of the same semantic action.

Provider identity strategy:

- Outlook immutable message ID is stored as `outlook:message:{immutable_id}`
- the value is persisted on the generic `ExecutionAttempt.external_reference` field

Retry behavior:

- if a prior non-ambiguous attempt already created a draft identity, retry reuses that same identity
- retry does not create a fresh provider draft
- a prior ambiguous Outlook attempt blocks blind resend and returns the same ambiguous posture

This preserves:

- one semantic action
- one provider message identity

## Verified Success Definition

Phase 8.7B does not claim inbox delivery.

`succeeded` means:

- Microsoft accepted the send request for the exact persisted draft identity
- one bounded verification read of that same message identity returned:
  - the same immutable message ID
  - `isDraft = false`
  - a non-empty `sentDateTime`

This is deliberately narrower than delivery confirmation and deliberately stronger than transport acceptance alone.

## Ambiguity Handling

Ambiguous outcomes fail closed.

Examples:

- timeout after draft send request
- TLS/connection loss during send
- inconclusive verification after send
- prior ambiguous attempt on the same semantic action

Normalized result:

- `adapter_outcome_ambiguous`

Required behavior:

- not success
- not blind retry
- persisted provider identity retained when available

## External Reference Persistence

No new persistence system was added for Outlook.

Reused generic surface:

- `ExecutionAttempt.external_reference`

No migration was required because the existing Phase 8 generic execution-attempt model already:

- allows provider identity on terminal failed attempts
- allows provider identity on retryable failed attempts
- allows provider identity on ambiguous failed attempts
- protects successful external-reference collisions

## Confidentiality

Phase 8.7B keeps execution persistence narrow:

- no credentials persisted
- no auth headers persisted
- no bearer tokens persisted
- no client secrets persisted
- no raw email body dumped into audit payloads

Persisted execution metadata remains limited to:

- provider status
- normalized error or success details
- external provider message reference

## Known Limitations

- reply execution is intentionally deferred
- reply-all is unsupported
- attachments are unsupported
- recipient authority is explicit-structured only, not yet backed by a canonical contact-email authority layer
- no delivery confirmation beyond bounded provider verification exists
- no reconciliation worker exists for ambiguous provider outcomes
- no inbound Outlook processing exists

## Result

Phase 8.7B closes successfully as a controlled outbound client-email execution slice.

It proves the client-facing send boundary without bypassing governance and without broadening into inbound email or end-to-end rental workflow assembly.
