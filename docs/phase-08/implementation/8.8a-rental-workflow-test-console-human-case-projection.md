# 8.8A Rental Workflow Test Console & Human Case Projection

## What Was Implemented

Added a minimal internal console that:

- creates isolated test `RentalCase` records
- reads a complete Phase 8 case snapshot through existing repositories
- shows observations, facts, approvals, actions, attempts, follow-ups, reasoning, and workflow events
- injects raw test evidence without pretending inbound Outlook exists
- injects structured test observations through the existing Phase 8.3 observation runtime
- previews a read-only Living Working Proposal / Case Overview
- executes existing guarded runtime entry points instead of direct table edits

## Why Standard-Library WSGI

The repository did not already contain a web application framework.

Using:

- Python standard library
- server-rendered HTML
- existing repository/runtime modules

kept the console:

- small
- local-first
- dependency-light
- aligned with the existing Python runtime surface

## Local Run Command

```bash
python3 -m tools.phase_08_workflow.test_console
```

Optional environment controls:

```bash
WORKFLOW_TEST_CONSOLE_HOST=127.0.0.1
WORKFLOW_TEST_CONSOLE_PORT=8765
WORKFLOW_TEST_CONSOLE_ALLOW_NON_LOCAL_BIND=false
WORKFLOW_TEST_CONSOLE_ALLOW_REAL_PROVIDERS=false
```

## Developer Runbook

### Start

1. Start local Supabase if it is not already running.
2. Launch the console:

```bash
python3 -m tools.phase_08_workflow.test_console
```

3. Open the printed localhost URL.

### Create Test Rental

1. Use `Create Test Rental`.
2. Provide any optional label, company label, contact email, or event reference.
3. The console persists a real `RentalCase` plus a `test_console_case_registered` workflow event marker.

### Inject Evidence

1. Open a test case.
2. Use `Inject Raw Test Evidence` for pasted inbound-style message content.
3. This stores:
   - an inbound source record
   - a test-console workflow event containing the raw payload

### Inject Structured Observation

1. Use `Inject Structured Test Observation`.
2. Select a governed field code and observation shape.
3. Provide a value compatible with the field contract.
4. The console routes the request through `ingest_structured_observations(...)`.

### Inspect Case

Open a test case detail page to inspect:

- case state
- facts
- observations / evidence
- questions
- requirements
- blockers
- changes
- decisions
- approvals
- actions
- execution attempts
- follow-ups
- reasoning projections
- workflow events

### Approve

Use `Approve` or `Reject` on an open approval request.

This calls:

- `apply_approval_decision(...)`

### Execute

Use `Execute` on a `ready_to_execute` action.

Default execution modes are deterministic fake modes:

- fake success
- fake retryable failure
- fake permanent failure
- fake timeout
- fake ambiguous

Real provider mode is only shown when explicitly enabled at environment level.

### Real Provider Mode

Set:

```bash
WORKFLOW_TEST_CONSOLE_ALLOW_REAL_PROVIDERS=true
```

When enabled:

- `email` actions map to Outlook / Microsoft Graph
- `task_surface` actions map to Asana
- the console shows `REAL PROVIDER EXECUTION ENABLED`

The console still does not allow arbitrary recipient, sender, or project overrides.

### Cleanup

This phase does not expose a delete business function.

Preferred cleanup:

1. local `supabase db reset`
2. rebuild local fixture state as needed

## Safety Notes

- UI business rules implemented: `0`
- direct lifecycle mutation from browser UI: `0`
- direct action status edits from browser UI: `0`
- direct adapter calls from browser UI: `0`
- browser-exposed Supabase credentials: `0`
- browser-exposed Asana credentials: `0`
- browser-exposed Outlook credentials: `0`
- real provider execution enabled by default: `0`

## Known Limitations

- no inbound Outlook ingestion exists yet
- raw evidence storage is a test harness boundary, not the future inbound email architecture
- no production auth system is introduced here
- no document generation or DOCX output is added
- no cleanup delete UI is exposed
