# Phase 8.8B - Inquiry Intake Promotion Runtime

Date completed: 2026-08-14

## Scope

Phase 8.8B implements the first governed inquiry intake runtime that can promote structured inquiry observations into governed inquiry state without letting observations directly rewrite case truth.

Implemented:

- deterministic inquiry-intake evaluation for:
  - requested schedule
  - guest count
  - requested rental scope
  - event type
- a stable plan/apply runtime boundary:
  - `evaluate_inquiry_intake(...)`
  - `apply_inquiry_intake(...)`
- structured intake plan and commit contracts
- in-memory and Supabase repository commit paths with optimistic case-revision checks
- idempotent core `OpenQuestion` creation and resolution
- safe current-vs-change handling through existing `ProposedCaseChange` and `RescheduleRequest` entities
- Test Console `Run Inquiry Intake` control
- Working Proposal projection updates for promoted inquiry truth
- a schedule-ingestion remediation so fresh or incomplete schedule observations no longer fabricate `RescheduleRequest` rows before inquiry intake decides what to do

Explicitly not implemented:

- follow-up creation
- `REQUEST_CLIENT_INFORMATION`
- client email sends
- Outlook inbound transport
- AI extraction from raw email
- capacity, pricing, availability, or other feasibility evaluation
- lifecycle advancement

Planned semantic effects are explicit and machine-readable:

- `promote_current_value`
- `create_open_question`
- `resolve_open_question`
- `create_proposed_change`
- `create_reschedule_request`
- `no_change`

Each effect carries:

- rental-case scope
- inquiry field code
- expected case revision

- current value where relevant
- proposed value where relevant
- reason code
- stable effect idempotency key

## Promotion Rules

Observation eligibility is intentionally narrow:

- case-associated only
- `status = validated`
- matching persisted observation effect required
- effect disposition cannot be:
  - `reject_quarantine`
  - `manual_mapping_required`
  - `case_association_required`

Current-value promotion rules:

- schedule promotes only from a complete, structurally valid start/end pair
- guest count promotes only from a positive integer
- scope promotes only from specific governed scope values:
  - `studio_space`
  - `entire_venue`
- event type promotes only from a non-empty normalized string

Open-question rules:

- unresolved schedule -> `requested_event_timing`
- unresolved guest count -> `expected_guest_count`
- unresolved scope -> `requested_rental_scope`
- unresolved event type -> `requested_event_type`
- repeated evaluation reuses the same semantic question instead of creating duplicates
- later valid evidence resolves the question in place instead of deleting history

Conflict rules:

- no current truth + conflicting eligible candidates -> no winner selected
- current truth + one different candidate -> governed change object
- current truth + multiple different candidates -> current truth preserved and no silent winner selected

## Current-vs-Change Boundary

The runtime now distinguishes:

- no current schedule + complete valid schedule candidate -> current requested schedule
- current schedule + different complete schedule candidate -> `RescheduleRequest`
- no current guest count + exact value -> current guest-count fact
- current guest count + different value -> `ProposedCaseChange`
- no current scope + specific governed scope -> current rental scope
- current scope + different governed scope -> `ProposedCaseChange`
- no current event type + valid normalized event type -> current event-type fact
- current event type + different normalized event type -> `ProposedCaseChange`

The runtime never silently overwrites established current truth.

## Atomicity And Revision Safety

No schema migration was required for this slice.

Reason:

- current governed storage already existed for all four promoted fields
- existing `OpenQuestion`, `ProposedCaseChange`, `RescheduleRequest`, and `WorkflowEvent` tables were sufficient
- the existing repository pattern already supported an atomic multi-record commit boundary

Commit behavior:

- evaluation binds to `expected_revision`
- commit fails closed on stale case revision
- one successful material application increments case revision exactly once
- schedule and scope update on the `RentalCase`
- guest count and event type upsert through `rental_case_facts`
- question creation, resolution, proposed changes, reschedules, and workflow events happen in the same commit boundary
- workflow events use `event_identity_key = effect.idempotency_key`
- Supabase event insertion uses `on conflict (rental_case_id, event_identity_key) do nothing`

## Provenance Strategy

Promoted inquiry truth does not lose its source observation trail.

Persistence strategy:

- promoted facts store `source_reference = inbound_observation:{id}`
- created and resolved questions store the primary observation reference
- created proposed changes and reschedule requests store the primary observation reference
- workflow events record:
  - field code
  - effect code
  - reason code
  - source observation ids
  - current value
  - proposed value
  - case revision

Event types used:

- `case_fact_promoted_from_observation`
- `inquiry_open_question_created`
- `inquiry_open_question_resolved`
- `inquiry_change_proposed`
- `inquiry_reschedule_requested`

## Schedule-Ingestion Remediation

The live console validation on Friday, August 14, 2026 exposed a real contradiction:

- fresh complete schedule observations were still creating `RescheduleRequest` rows during observation ingestion
- incomplete schedule observations could also create `RescheduleRequest` rows from nothing

This was corrected in `tools/phase_08_workflow/observations.py`.

New ingestion behavior:

- incomplete or structurally invalid schedule payload -> `no_workflow_effect`
- no current governed schedule + complete schedule candidate -> `no_workflow_effect`
- only an already-established current governed schedule plus a different complete schedule candidate may create `create_reschedule_request`

This preserves the required architecture:

```text
observation inserted
-> evidence preserved
-> inquiry intake decides current truth or open question
```

not:

```text
fresh inquiry schedule
-> reschedule from nothing
```

## Known Limitations

- `custom_scope` is intentionally not promoted as established current scope because it is still serving as the unresolved placeholder for fresh test-console cases
- later change observations may already create a governed proposed change or reschedule object through the earlier Phase 8.3 observation-ingestion path; inquiry intake suppresses duplicate semantic effects instead of creating a second object
- the Working Proposal intentionally keeps observed candidates visible next to current truth; evidence visibility is preserved rather than hidden after promotion
- this slice still does not create waiting-state workflow, follow-ups, or outbound client actions
