# Phase 8.2 - Deterministic Lifecycle & Guard Engine

Date completed: 2026-08-09

## Scope

Phase 8.2 implements the deterministic lifecycle engine that sits on top of the Phase 8.1 persistence foundation.

Implemented:

- typed lifecycle evaluation and failure-result contracts
- frozen normal-transition graph enforcement
- deterministic guard evaluation by target lifecycle state
- in-memory and Supabase-backed lifecycle repository support
- atomic lifecycle commit helper integration
- manual override commit path
- readiness re-evaluation and degradation signaling
- lifecycle replay and audit validation
- focused Python and DB regression coverage

Explicitly not implemented:

- observation intake
- natural-language interpretation
- autonomous workflow planning
- outbound adapter execution
- reminders, scheduling, agents, or UI
- answer generation or freeform workflow truth

## Contract Layer Added

`tools/phase_08_workflow/lifecycle_types.py` introduces the deterministic engine result surface:

- lifecycle failure codes
- `GuardResult`
- `TransitionEvaluation`
- `LifecycleTransitionResult`
- `ManualTransitionOverrideRequest`
- `LifecycleCaseEvaluation`
- `ReadinessReevaluation`
- `LifecycleHistoryValidationResult`

These contracts keep engine behavior structured and machine-checkable. No prose output is required to understand why a transition passed or failed.

## Lifecycle Evaluation Engine

`tools/phase_08_workflow/lifecycle_engine.py` now owns:

- the frozen normal transition graph for all 12 lifecycle states
- terminal-state handling
- structured invalid-target and case-not-found outcomes
- read-only transition evaluation
- mutation-bearing transition application with revision checks
- explicit manual override application
- readiness re-evaluation
- case-state evaluation across all legal outgoing transitions

Important behavior:

- normal illegal edges fail closed and mark `manual_override_required`
- terminal outbound transitions are never normally legal
- allowed edges are still subject to deterministic guard evaluation
- stale revisions reject before mutation
- commits increment revision exactly once

## Guard Layer

`tools/phase_08_workflow/lifecycle_guards.py` implements target-specific deterministic guard logic.

Guard families implemented:

- conflicting active case-decision detection
- minimum eligibility to begin proposal work
- proposal rework reopening
- confirmation rework reopening
- proposal pending client readiness
- structured client-intent confirmation requirement
- confirmation completion requirements
- readiness blockers, requirements, questions, approvals, material changes, and artifact freshness
- readiness degradation back to `confirmed_pre_event`
- event-start evidence
- event-completion evidence
- close-out gating
- dormancy metadata validation
- dormant resume-target enforcement

Important design choices:

- dormant resume restores only the stored resume target rather than treating resume as fresh forward progression
- approval-type fallback applies only when the approval is not already explicitly targeted at another lifecycle gate
- event evidence is structured and payload-based, not derived from prose

## Repository And Atomic Commit Support

`tools/phase_08_workflow/lifecycle_repository.py` adds:

- `LifecycleCaseSnapshot`
- `LifecycleRepositoryProtocol`
- `InMemoryLifecycleRepository`
- `SupabaseLifecycleRepository`

The Supabase repository delegates atomic mutation to:

- `private.commit_rental_case_lifecycle_transition(...)`

That SQL helper:

- locks the target case row
- enforces expected revision and expected current state
- increments case revision once
- writes workflow event and lifecycle history rows in one transaction
- persists dormant metadata only while the case is dormant
- supports explicit manual override audit fields

Business legality remains in Python. The SQL helper is intentionally commit-oriented, not policy-oriented.

## Replay Validation

`tools/phase_08_workflow/lifecycle_replay.py` validates persisted lifecycle history against the frozen graph.

It detects:

- illegal normal edges
- broken state chains
- revision discontinuities
- final-state mismatch
- final-revision mismatch

Manual overrides can legally bridge edges that would otherwise be invalid.

## Boundary Preserved

Phase 8.2 stops at deterministic legality, guards, commit safety, and replay.

It does not yet decide:

- what new workflow facts should be created from inbound communication
- what actions should be planned next
- how actions are executed or retried
- how humans review or operate the workflow
- how generated responses are drafted

That boundary remains intentionally intact for the next implementation layer.
