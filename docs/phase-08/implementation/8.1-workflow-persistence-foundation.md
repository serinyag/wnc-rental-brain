# Phase 8.1 - Workflow Persistence Foundation

Date completed: 2026-08-09

## Scope

Phase 8.1 implements only the persistence and typed-contract foundation for the frozen Phase 8 workflow architecture.

Implemented:

- canonical workflow persistence tables
- lifecycle-state persistence and append-only transition history
- normalized workflow facts, decisions, approvals, actions, attempts, follow-ups, milestones, artifacts, and reasoning projections
- deterministic database constraints, partial uniqueness, same-case foreign keys, and append-only protections
- Phase 8 typed Python contracts and structural validation
- focused Phase 8 DB and Python tests

Explicitly not implemented:

- lifecycle engine / transition evaluation
- inbound email extraction
- workflow evaluation
- Phase 7 runtime reasoning execution
- external actions or integrations
- scheduling, retries, agents, UI, or persistence consumers

## Schema Namespace Decision

Canonical workflow entities were placed in `public`.

Rationale:

- Phases 4-6 already keep canonical governed entities in `public`
- Phase 8 rows are first-class domain records, not internal helper state
- future runtime readers and writers need stable, normalized relational surfaces

Workflow-specific helper functions were placed in `private`:

- `private.workflow_text_array_values_nonempty(...)`
- `private.workflow_text_array_values_allowed(...)`
- `private.workflow_append_only_guard()`

This keeps Phase 8 logically distinct from:

- Phase 4 deterministic authority tables
- Phase 5 knowledge storage
- Phase 6 historical precedent storage

No Phase 4, 5, or 6 source-of-truth tables were repurposed for workflow state.

Key persistence outcomes:

- `RentalCase` is the aggregate root with stable UUID, stable case code, explicit lifecycle state, and monotonic `case_revision`
- all 12 frozen lifecycle states are enforced by SQL check constraints
- workflow history is normalized instead of being embedded in JSON on the case row
- case-specific truth remains scoped to `rental_case_id`
- material overrides stay proposed or approved in workflow rows rather than mutating Phase 4
- action intent is stored separately from execution history
- artifact freshness and reasoning provenance are minimally persistable without storing full prompts or ContextPackages

## Constraints, Indexes, and Safety Posture

Core constraint posture:

- check-constrained text values instead of Postgres enums, matching repository style
- `case_reference_code` uniqueness and format validation
- non-negative `case_revision`
- append-only protections for workflow facts and audit history
- partial unique index for one active `CaseDecision` per `(rental_case_id, domain_code, scope_key)`
- unique attempt numbers per `WorkflowAction`
- unique event identity per case when an identity key is provided
- required accepted-change and approval references enforced where architecture required them

Operational indexes:

- active cases by lifecycle state
- event dates
- open requirements
- unresolved questions
- open blockers
- active proposed changes
- active reschedule requests
- pending approvals
- pending and failed actions
- follow-up due times
- milestone target times
- artifact freshness
- reasoning projection recency
- active case decisions by case/status and by active scope

## Same-Case Foreign-Key Protection

Direct same-case relational enforcement was added where practical, including:

- lifecycle transition -> triggering workflow event
- requirement -> waiver case decision
- decision -> superseded decision
- reschedule request -> linked proposed change
- decision -> linked approval request
- execution attempt -> workflow action
- milestone -> requirement
- milestone -> workflow action
- case current proposal / agreement artifact pointers -> case artifacts

These constraints prevent silent cross-case linkage for the directly modeled relationships.

## Append-Only and Deletion Posture

Append-only tables protected by trigger:

- `public.workflow_events`
- `public.rental_case_lifecycle_transitions`
- `public.workflow_execution_attempts`
- `public.rental_case_reasoning_projections`

Mutable current-state tables use `private.touch_updated_at()` triggers.

Deletion posture:

- `on delete restrict` is used throughout the workflow aggregate
- deleting a `RentalCase` does not cascade through workflow history
- supersession and terminal statuses are the preferred lifecycle for historical records

## JSON Usage Discipline

`jsonb` is used only where the architecture requires variable structured payloads:

- event payloads
- proposed / effective / accepted values
- candidate date sets
- action payloads
- approval decision payloads
- execution response snapshots
- degraded retrieval summaries

Normalized core workflow state remains relational.

   `python3 -m tools.phase_05_chunking.generate_bulk --load-db`

These were local verification prerequisites, not new runtime features.

## Accepted Limitations

- polymorphic references such as generic `target_entity_type` and `reason_entity_type` cannot be fully foreign-key enforced in SQL; application validation still owns the remaining integrity surface
- lifecycle transition legality is intentionally not enforced in SQL yet; Phase 8.2 owns evaluation and transition policy
- no workflow action executor, scheduler, retry worker, or approval orchestrator is implemented in Phase 8.1
- reasoning projection persistence is intentionally minimal and does not store full Phase 7 context packages or prompts
- RLS is enabled and table privileges are revoked, but policy definitions are intentionally deferred until runtime access patterns are frozen
