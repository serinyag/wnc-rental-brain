# Phase 8.8D - Inquiry Response Drafting + Simulated Outlook Mailbox

Date completed: 2026-08-15

## Scope

Phase 8.8D adds a controlled test-console workflow for drafting inquiry-response emails without introducing any real mailbox side effects.

Implemented path:

1. current `REQUEST_CLIENT_INFORMATION` workflow action
2. bounded draft generation from structured current state
3. immutable draft revision persistence
4. exact revision approval binding
5. human edit or regenerate -> new revision
6. simulated send through existing execution runtime

Not implemented:

- real Microsoft Graph send from this slice
- mailbox polling
- reply threading against a real Outlook message id
- live sent-items sync
- autonomous send

## Design choices

### 1. Narrow persistence extension

The generic artifact table was not sufficient for immutable, exact-revision client draft review.

Instead, this slice adds:

- `public.inquiry_response_draft_revisions`

Each row stores:

- workflow-action linkage
- conversation key
- source case revision
- immutable structured draft content
- approval request linkage
- send outcome linkage
- current-vs-history state

This keeps approval and execution in the existing runtime while giving drafts their own revision-safe persistence.

### 2. Structured draft content instead of free-form-only editing

The draft model stores:

- subject
- salutation
- intro text
- per-question prompt lines
- closing text
- signoff

The rendered email body is deterministic from those parts.

Reason:

- required-question coverage can be validated deterministically
- human edits remain allowed
- a human edit still creates a new immutable revision

### 3. Approval stays on workflow actions

This slice deliberately reuses the existing workflow-action approval machinery.

Exact-revision safety is achieved by:

- linking each current draft revision to one approval request
- cancelling/replacing open approvals when a newer revision is created
- creating a successor workflow action when an already-approved action is edited

Result:

- old approval never authorizes the new revision
- existing execution gates remain intact

### 4. Simulated send reuses execution runtime

Send simulation still flows through:

```text
WorkflowAction
-> execute_workflow_action(...)
-> fake adapter registry
-> ExecutionAttempt
-> normalized outcome
```

This slice does not insert a fake sent item directly into a separate mailbox store.

Instead:

- draft revision state is updated from the execution result
- the console mailbox view reflects that persisted workflow/testing state

## Console behavior

The case detail page now includes a `Simulated Outlook Mailbox` section that shows:

- inbound raw-evidence items as the simulated inbox
- inquiry-response draft threads
- generate / regenerate controls
- edit form for the current draft
- exact-revision approve / reject controls
- simulate-send controls for approved current drafts
- revision history

The Working Proposal remains unchanged in role:

- communication summary only
- not a mailbox
- not a second truth store

## Safety boundaries

Guaranteed in this slice:

- real Outlook calls = `0`
- real Asana calls = `0`
- model-selected approval posture = `0`
- model-selected recipient = `0`
- edited-after-approval executable with old approval = `0`
- stale draft approvable as current = `0`
