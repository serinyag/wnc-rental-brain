# Phase 8.8C - Inquiry Waiting & Follow-Up Slice

Date: Friday, August 14, 2026

## Goal

Turn unresolved inquiry-stage intake questions into governed waiting state and then into structured follow-up work, without sending anything externally.

## Design choices

### 1. Separate waiting runtime, reused follow-up execution runtime

The slice adds:

- `tools/phase_08_workflow/inquiry_waiting.py`

and deliberately reuses:

- persisted `rental_case_follow_ups`
- `evaluate_due_follow_ups(...)`
- existing orchestration action idempotency and supersession

This avoided building a duplicate follow-up engine.

### 2. Semantic inquiry follow-up identity

`public.rental_case_follow_ups` was extended with:

- `semantic_identity_key`
- `sequence_number`
- `context_payload`

This was the narrowest useful persistence addition because the original table could not safely express:

- one semantic inquiry waiting episode
- follow-up `#1` versus `#2`
- multiple unresolved question references on one follow-up

### 3. Open questions no longer create immediate client request actions

`orchestration_runtime._apply_open_question_rules(...)` still creates blockers for unresolved client questions, but it no longer creates an immediate outbound `REQUEST_CLIENT_INFORMATION` action.

The new path is:

```text
open client questions
→ inquiry waiting runtime
→ semantic inquiry follow-up
→ orchestration follow-up rule
→ structured request action when current
```

### 4. Follow-up payloads are now rich enough for inquiry work

Inquiry follow-up actions now carry:

- `follow_up_id`
- `reason_code`
- `sequence_number`
- `open_question_ids`
- `required_field_codes`
- `intended_recipient_role`
- optional `recipient_reference`
- `purpose`
- `reason`
- `question_texts`
- `summary`

That keeps the drafting boundary structured and deterministic.

### 5. Partial and full responses are handled by semantic refresh, not duplication

Partial response:

- reuses the same semantic follow-up
- drops resolved questions from `context_payload`
- supersedes stale current request action
- creates a refreshed request action for remaining unresolved questions

Full response:

- cancels the inquiry follow-up
- supersedes the stale request action
- relies on existing execution guards to reject later stale execution attempts

### 6. Time-critical inquiries escalate safely

No CRM scoring system was invented.

The first implementation uses deterministic event proximity only:

- cold inquiry default cadence: `7` days
- max cold follow-up sequence: `2`
- urgent event threshold: `3` days

Urgent inquiry waiting escalates into governed internal work instead of silent dormancy.

## Console impact
