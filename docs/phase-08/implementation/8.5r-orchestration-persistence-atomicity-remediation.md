# Phase 8.5-R - Orchestration Persistence & Atomicity Remediation

Date completed: 2026-08-13

## Scope

Phase 8.5-R closes the four runtime-hardening blockers that kept Phase 8.5 orchestration from handing off into execution and follow-up runtime.

Closed blockers:

- B1: no Supabase-backed orchestration repository
- B2: no transactional atomic orchestration commit
- B3: incomplete `WorkflowEvent` audit coverage
- B4: workflow-action approval targets lacked controlled action-state mutation

This remediation still does not implement:

- external action execution
- execution retries or scheduling
- lifecycle transition selection
- answer generation
- agents, UI, or deployment

## Implementation Summary

### 1. Supabase Repository Completion

`SupabaseWorkflowOrchestrationRepository` now exposes production-shaped persisted orchestration behavior for:

- full case-snapshot loading
- ready-to-execute action listing
- case-decision approval application
- workflow-action approval application
- proposed-case-change resolution

The repository now maps DB helper `failure_code` outputs back into typed orchestration `failure_codes` so the Supabase path matches the fail-closed in-memory contract.

### 2. Atomic DB Helper Surface

`supabase/migrations/20260813000200_phase_08_orchestration_atomicity_remediation.sql` now defines:

- `private.commit_phase8_case_decision_approval(...)`
- `private.commit_phase8_workflow_action_approval(...)`
- `private.commit_phase8_proposed_case_change_resolution(...)`
- `private.phase8_reference_id(...)`

These helpers atomically protect:

- approval decision rows
- case-decision activation or rejection
- workflow-action approval release or cancellation
- proposed-change acceptance or rejection
- case revision increments
- artifact freshness updates
- stale-action supersession
- blocker resolution
- append-only workflow-event audit writes

The helper functions now declare `#variable_conflict use_column` so output-column names do not shadow unqualified DML columns during execution.

### 3. Workflow-Action Approval State Machine

Workflow-action approvals are now governed by application-controlled transitions only:

- `awaiting_approval -> approved -> ready_to_execute` for `approval_required`
- `awaiting_approval -> approved -> ready_to_execute` for `automatic_allowed`
- `awaiting_approval -> approved` for `human_only`
- `awaiting_approval -> cancelled` on rejection

Approval never executes the action.

The action remains a persisted intent record that later runtime phases may consume.

### 4. Audit Completion

Material orchestration mutations now append structured `workflow_events` for:

- approval decisions
- case-decision activation or rejection
- workflow-action status changes
- blocker resolution
- artifact freshness changes
- workflow-action supersession
- case-fact changes
- proposed-change acceptance or rejection

This closes the audit gap that previously blocked readiness.

### 5. Activation Helper Hardening

The convenience case-decision activation helper is now guarded against mismatched approval-to-decision references so it cannot activate unrelated case decisions through a stale or incorrect approval link.
