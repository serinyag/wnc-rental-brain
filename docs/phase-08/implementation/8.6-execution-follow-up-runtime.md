# Phase 8.6 - Execution & Follow-Up Runtime

Date completed: 2026-08-13

## Scope

Phase 8.6 implements the deterministic runtime that executes already-governed `WorkflowAction` records and evaluates persisted `FollowUp` records without bypassing orchestration.

Implemented:

- execution input, result, and follow-up evaluation contracts
- provider-neutral execution adapter protocol and registry
- deterministic fake adapters for:
  - success
  - retryable failure
  - permanent failure
  - timeout
  - malformed result
  - exception
- stable execution entry points:
  - `execute_workflow_action(...)`
  - `execute_ready_workflow_actions(...)`
  - `evaluate_due_follow_ups(...)`
- in-memory and Supabase-backed execution-attempt repository support
- atomic DB helpers for execution start, execution completion, and follow-up status update
- controlled `workflow_execution_attempts` completion-update guard
- focused Python and DB regression coverage

Explicitly not implemented:

- live external providers
- autonomous retry queues
- RAG, agents, UI, deployment, or anything from Phase 8.7+

## Stable Runtime Boundary

Phase 8.6 now follows the required controlled boundary:

```text
persisted WorkflowAction
-> execution eligibility checks
-> provider-neutral adapter lookup
-> ExecutionAttempt start commit
-> deterministic fake adapter invocation
-> NormalizedExecutionResult
-> atomic attempt/action completion commit
-> optional follow-up state update
-> orchestration re-entry when safe
```

No execution path invents new work or executes model prose.

## Adapter Layer

`tools/phase_08_workflow/execution_runtime.py` defines:

- `ExecutionAdapterProtocol`
- `ExecutionAdapterRegistry`
- `DeterministicFakeExecutionAdapter`
- helper fake adapter factories for all required deterministic test outcomes

The adapter receives only:

- the persisted structured action intent
- execution context
- semantic idempotency context

The adapter does not:

- choose the action
- change approval posture
- advance lifecycle state
- decide external business truth

## Repository Layer

`tools/phase_08_workflow/orchestration_repository.py` now exposes:

- execution-attempt listing
- follow-up listing for due-state evaluation
- execution start commit
- execution completion commit
- follow-up status update commit

The case snapshot now also carries `execution_attempts`, which keeps in-memory and Supabase behavior aligned for runtime inspection and testing.

## Execution Semantics

The runtime now fails closed for:

- case not found
- action not found
- stale action revision
- action not due
- `human_only`
- `blocked`
- `cancelled`
- `superseded`
- unavailable adapter
- malformed adapter result

Key execution behaviors:

- every real invocation creates one started `ExecutionAttempt`
- verified success is required before an action becomes `succeeded`
- retry-eligible failures return the same action to `ready_to_execute`
- already-succeeded actions short-circuit idempotently without reinvocation
- malformed or exception outcomes never become success

## Follow-Up Semantics

Follow-up runtime behavior now stays inside the governed workflow loop:

- scheduled due work becomes `due`
- attempted due work can become `overdue`
- escalation thresholds can move follow-ups to `escalated`
- completed and cancelled follow-ups are terminal
- due follow-up evaluation re-enters normal orchestration and creates structured `WorkflowAction` intent only
- follow-up evaluation never calls an adapter directly

## DB Remediation

The main persistence contradiction discovered during inspection was the blanket append-only update guard on `workflow_execution_attempts`.

That guard has now been refined so:

- immutable attempt identity fields still cannot change
- deletes are still blocked
- only a single legal `started -> terminal` completion update is allowed

This preserves the append-only spirit of execution history without making action completion impossible.
