# Phase 8.3 - Inbound Observation & Proposed Change Foundation

Date completed: 2026-08-10

## Scope

Phase 8.3 implements the safe inbound interpretation boundary between future external inputs and canonical workflow truth.

Implemented:

- canonical Phase 8.2 handoff marker normalization
- provider-neutral inbound source record contracts
- structured observation contracts and failure taxonomy
- governed observation field registry derived from live workflow domains and the current data dictionary
- deterministic case-association boundary
- in-memory observation repository and stable ingestion entry point
- safe routing to proposed workflow effects only
- minimal persistence support for governed case facts, inbound sources, observations, and observation effects
- focused Python and DB regression coverage

Explicitly not implemented:

- live Outlook, platform, or supplier integrations
- LLM extraction providers
- direct material truth activation from observations
- lifecycle transitions from observation insertion
- approval activation, action planning, or execution
- UI, agents, persistence consumers, or answer generation

## Canonical Case-Fact Preflight

Preflight question:

> Where does an accepted structured rental fact actually live?

Observed live state:

- active event dates already have a canonical home in `rental_cases`
- case-specific exceptions already have a canonical home in `rental_case_decisions`
- material inbound changes already have a canonical home in `rental_case_proposed_changes`
- negotiated date changes already have a canonical home in `rental_case_reschedule_requests`
- requirements and open questions already have canonical homes in `rental_case_requirements` and `rental_case_open_questions`

Gap confirmed:

- many ordinary current-scope operational facts such as guest count, layout requirements, event-day contact, technical requirements, and facilitator or catering arrangement did not yet have a normalized governed current-state home

Decision:

- add minimal `RentalCaseFact` persistence support as implementation support for the frozen `RentalCase` "current scope snapshot" responsibility

What this does not mean:

- it does not create a second authority layer
- it does not let observation intake activate truth directly
- it does not override Phase 4 or `CaseDecision`

This therefore did not require stopping with `PHASE_8_CASE_FACT_MODEL_BLOCKER`.

## Contract Layer Added

`tools/phase_08_workflow/observation_contracts.py` now defines:

- provider-neutral source-system and record-type vocabularies
- source-association statuses
- observation types, statuses, claim kinds, target kinds, and dispositions
- `ObservationFieldDefinition`
- `RentalCaseFact`
- `InboundSourceRecord`
- `InboundObservation`
- `InboundObservationEffect`

Key contract invariants:

- confidence is bounded to `0 <= x <= 1`
- source and observation excerpts are limited to `500` characters
- resolved source records require a resolved case id
- target field and target domain must be set together
- one effect may link to at most one workflow target entity
- required dispositions must carry the expected linked workflow entity id

`tools/phase_08_workflow/observation_types.py` adds the application-facing ingestion surface:

- `InboundSourceRecordInput`
- `CaseAssociationInput`
- `StructuredObservationCandidate`
- `StructuredObservationIngestionRequest`
- `CaseAssociationResult`
- `ObservationDispositionResult`
- `ObservationIngestionResult`

## Repository And Stable Entry Point

`tools/phase_08_workflow/observation_repository.py` adds:

- `ObservationCaseSnapshot`
- `ObservationRepositoryProtocol`
- `InMemoryObservationRepository`

`tools/phase_08_workflow/observations.py` adds the stable application entry point:

- `ingest_structured_observations(...)`

The ingestion flow is now:

1. validate and dedupe the inbound source
2. resolve or fail closed on deterministic case association
3. validate each observation against the governed registry
4. persist the observation as evidence, never as direct truth
5. route to exactly one safe proposed workflow effect
6. create only bounded workflow records such as:
   - question-answer candidate
   - proposed change
   - proposed case decision
   - reschedule request
   - requirement evidence candidate
7. return structured machine-readable results

## Deterministic Case Association

Implemented deterministic association inputs:

- explicit `rental_case_id`
- explicit case reference code

Failure-closed behavior:

- missing association becomes `case_association_required`
- bad explicit references produce `case_not_found`
- no fuzzy LLM case matching is used

## Observation Routing

Implemented routing outcomes:

- `case_association_required`
- `manual_mapping_required`
- `reject_quarantine`
- `no_workflow_effect`
- `open_question_answer_candidate`
- `create_proposed_change`
- `create_case_decision_candidate`
- `create_reschedule_request`
- `record_confirmation_candidate`
- `record_requirement_evidence_candidate`

Routing rules preserved the requested architecture boundary:

- extraction is evidence, not authority
- high confidence never activates truth
- stale observations stay review-bound
- lifecycle state is never chosen inside observation ingestion

## Proposed Change Behavior

When a governed case fact already exists and the incoming candidate value differs:

- the prior value is preserved
- the candidate becomes `ProposedCaseChange(status = proposed)`
- impact classification comes from explicit candidate input or conservative registry default
- review posture comes from registry policy
- canonical fact rows are not mutated by the ingestion step

Previously unknown values remain distinct from changed values:

- if a matching open question exists, the observation becomes a candidate answer
- otherwise the observation remains preserved evidence without silently mutating current truth

## Proposed Decision Behavior

Commercial or policy exception candidates such as `booking_fee_override` now route to proposed `CaseDecision` rows only.

Preserved:

- baseline reference
- proposed value payload
- scope key
- authority basis from source actor metadata
- approval posture
- evidence reference

Not allowed:

- activating the decision
- mutating Phase 4
- treating confidence or sender wording as approval

## Reschedule Behavior

Structured date or time changes targeting the active event window now route to `RescheduleRequest`.

Preserved:

- current active date snapshot
- requested date payload
- consequence summary shell with observation provenance
- urgency posture
- initial proposed status

Not allowed:

- changing `rental_cases.active_event_start` or `active_event_end`
- checking availability
- calculating cancellation or financial consequences
- transitioning lifecycle state

## Question-Answer Candidate Behavior

When an observation matches an existing related open question:

- `OpenQuestion` moves to `answered_pending_validation`
- the candidate answer payload is stored
- the observation provenance is linked through source reference and effect chain

It does not:

- directly resolve the question
- directly mutate canonical truth

## Requirement Evidence And Quarantine

Requirement evidence candidates can now attach bounded evidence references to same-case requirements.

If linkage is missing or unsafe:

- the observation routes to manual mapping
- cross-case attempts fail closed and are quarantined

Unknown or malformed observations now fail safely through:

- unmapped status
- quarantine disposition
- manual mapping required

## Stale Handling And Idempotency

Implemented:

- `observed_against_case_revision`
- stale detection against the live case revision
- `revalidation_required`
- deterministic source dedupe
- deterministic observation identity within a source

Replaying the same source now creates:

- `0` duplicate source rows
- `0` duplicate proposed changes
- `0` duplicate proposed decisions
- `0` duplicate reschedule requests

## Accepted Limitations

Phase 8.3 intentionally stops short of:

- direct canonical fact activation from observations
- approval resolution
- requirement auto-satisfaction beyond evidence attachment
- automatic low-impact truth mutation
- provider-specific raw message archival
- live extraction adapters
- Phase 7 workflow-consumption logic

## Hard Stop

Phase 8.3 ends at safe proposed workflow effects and the persistence scaffolding required to audit them.

The next layer is:

- Phase 8 workflow consumption of Phase 7 outputs and downstream deterministic resolution logic

No work beyond that boundary was implemented in this slice.
